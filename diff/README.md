## شهریور ماه 1405

### <u>پیش‌گفتار</u>

هر کسی که مدتی با خط فرمان لینوکس یا یونیکس کار کرده باشد، دیر یا زود به این پرسش برخورده است: «این دو فایل چه فرقی با هم دارند؟» شاید دو نسخه از یک فایل پیکربندی داشته باشید و نخواهید هرکدام را جداگانه بخوانید. شاید بخواهید بفهمید یک همکار دقیقاً چه تغییری در کد شما داده است. شاید بخواهید مطمئن شوید نسخه‌ی پشتیبان یک فایل، همان نسخه‌ی اصلی است یا نه. برای همه‌ی این موقعیت‌ها، یک ابزار کوچک و قدیمی وجود دارد که هنوز هم، بعد از نزدیک به پنجاه سال، در هر سیستم یونیکسی و لینوکسی حضور دارد: دستور diff.

دستور diff یکی از آن ابزارهایی است که شاید در نگاه اول ساده به نظر برسد، اما وقتی کمی عمیق‌تر به آن نگاه کنید، متوجه می‌شوید پایه و اساس بسیاری از فناوری‌هایی است که هر روز از آن‌ها استفاده می‌کنید. سیستم‌های کنترل نسخه مثل Git، ابزارهای مدیریت پیکربندی، سیستم‌های توزیع نرم‌افزار، و حتی روش‌هایی که برنامه‌نویس‌ها برای بررسی و مرور کد یکدیگر (Code Review) استفاده می‌کنند، همگی به نوعی بر پایه‌ی همان ایده‌ای ساخته شده‌اند که diff نزدیک به نیم قرن پیش معرفی کرد: پیدا کردن کوچک‌ترین مجموعه‌ی تفاوت‌ها بین دو نسخه از یک متن.

در این کتاب، قرار است با دستور diff از پایه تا سطح پیشرفته آشنا شوید. یاد می‌گیرید چگونه با diff دو فایل یا حتی دو پوشه‌ی کامل را با هم مقایسه کنید، چگونه خروجی آن را در قالب‌های مختلف بخوانید و تفسیر کنید، چگونه رفتار آن را با گزینه‌های گوناگون سفارشی کنید، و چگونه از آن برای ساختن و اعمال کردن وصله‌ها (patch) استفاده کنید. در پایان، نگاهی هم به جایگاه diff در دنیای واقعی می‌اندازیم، به‌ویژه در ابزارهایی مثل Git که همین امروز بخش بزرگی از دنیای نرم‌افزار را می‌چرخانند.

### این کتاب برای چه کسانی مناسب است

این کتاب برای هر کسی نوشته شده که با خط فرمان لینوکس، یونیکس یا macOS سروکار دارد، از برنامه‌نویسانی که هر روز با کد و کنترل نسخه کار می‌کنند گرفته تا مدیران سیستمی که باید فایل‌های پیکربندی را مقایسه و مدیریت کنند. اگر تازه با خط فرمان آشنا شده‌اید، فصل‌های ابتدایی کتاب مفاهیم پایه را قدم‌به‌قدم توضیح می‌دهند. اگر هم سال‌هاست با diff کار می‌کنید، فصل‌های میانی و پایانی کتاب به سراغ نکات ریزتر و کاربردهای پیشرفته‌تر می‌روند که شاید تا امروز با آن‌ها آشنا نشده باشید.

### در این کتاب چه چیزی خواهید یافت

در فصل ۱، «آشنایی با اصول diff»، با تاریخچه‌ی این ابزار، نحوه‌ی نصب آن، و ساده‌ترین شکل استفاده از آن آشنا می‌شوید. همچنین یک درک شهودی از این‌که diff اصلاً چگونه «تفاوت» را پیدا می‌کند، به دست می‌آورید.

در فصل ۲، «فرمت‌های خروجی diff»، یاد می‌گیرید diff می‌تواند تفاوت‌ها را به چند شکل مختلف نشان دهد: فرمت عادی (normal)، فرمت متنی (context)، فرمت یکپارچه (unified)، و فرمت کنار هم (side-by-side). هر کدام از این فرمت‌ها کاربرد خاص خودشان را دارند، و در این فصل یاد می‌گیرید هرکدام را کجا و چرا استفاده کنید.

در فصل ۳، «کنترل رفتار diff با گزینه‌ها»، به سراغ ده‌ها گزینه‌ای می‌رویم که diff در اختیار ما می‌گذارد؛ از نادیده گرفتن تفاوت در فاصله‌های خالی گرفته تا نادیده گرفتن بزرگی و کوچکی حروف، نادیده گرفتن خطوط خالی، و کنترل دقیق تعداد خطوط زمینه (context).

در فصل ۴، «مقایسه‌ی پوشه‌ها و مجموعه فایل‌ها»، خواهید دید diff تنها برای دو فایل تنها نیست؛ می‌توان با آن دو پوشه‌ی کامل، حتی با زیرپوشه‌های تودرتو، را با هم مقایسه کرد.

در فصل ۵، «diff و patch: ساخت و اعمال وصله»، وارد یکی از مهم‌ترین کاربردهای عملی diff می‌شویم: تبدیل خروجی diff به یک فایل وصله (patch) که می‌توان آن را برای دیگران فرستاد یا روی نسخه‌ای دیگر از همان فایل اعمال کرد.

و در نهایت، در فصل ۶، «diff در دنیای واقعی»، نگاهی می‌اندازیم به این‌که چگونه ابزارهایی مثل Git از همین مفاهیم diff استفاده می‌کنند، و چگونه می‌توان diff را در اسکریپت‌های شل و ابزارهای خودکارسازی به کار برد.

### آنچه لازم دارید

برای دنبال کردن این کتاب، تنها به یک سیستم لینوکس، یونیکس یا macOS نیاز دارید که دسترسی به ترمینال داشته باشد. دستور diff معمولاً از قبل روی همه‌ی توزیع‌های لینوکسی و روی macOS نصب است، چون بخشی از بسته‌ی GNU diffutils است که همراه سیستم‌عامل عرضه می‌شود. در فصل ۱ نحوه‌ی بررسی و در صورت نیاز نصب آن را توضیح می‌دهیم.

هیچ دانش برنامه‌نویسی خاصی لازم نیست، هرچند آشنایی مقدماتی با خط فرمان و ویرایشگرهای متنی به شما کمک می‌کند مثال‌ها را راحت‌تر دنبال کنید.

## فصل ۱

### <u>آشنایی با اصول diff</u>

پیش از آن‌که وارد جزئیات فنی دستور diff شویم، خوب است بدانیم این ابزار از کجا آمده، چه مشکلی را حل می‌کند، و اصلاً چگونه «تفاوت» بین دو فایل را پیدا می‌کند. درک این مفاهیم پایه کمک می‌کند در فصل‌های بعدی، وقتی با گزینه‌ها و فرمت‌های مختلف diff روبه‌رو می‌شوید، بدانید دقیقاً چه اتفاقی پشت صحنه در حال رخ دادن است.

### ۱.۱ داستان کوتاه diff

دستور diff یکی از قدیمی‌ترین ابزارهای دنیای یونیکس است. ریشه‌ی آن به اوایل دهه‌ی ۱۹۷۰ میلادی و آزمایشگاه‌های بل (Bell Labs) در نیوجرسی آمریکا برمی‌گردد، جایی که سیستم‌عامل یونیکس هم در همان سال‌ها متولد شد. این ابزار را داگلاس مک‌ایلروی (Douglas McIlroy) به همراه جیمز هانت (James Hunt) طراحی کردند، و برای اولین بار در نسخه‌ی پنجم یونیکس در سال ۱۹۷۴ میلادی عرضه شد.

ایده‌ی اصلی پشت diff این بود: برنامه‌نویس‌ها و ویراستاران متن، دائماً با نسخه‌های مختلف یک فایل سروکار دارند. وقتی فایلی تغییر می‌کند، اغلب فقط بخش کوچکی از آن عوض شده، نه همه‌ی آن. پس چرا باید کل دو فایل را کنار هم بگذاریم و خط‌به‌خط بخوانیم تا بفهمیم چه چیزی تغییر کرده؟ به‌جای آن، بهتر است ابزاری داشته باشیم که به‌طور خودکار کوچک‌ترین و دقیق‌ترین توصیف ممکن از تفاوت بین دو فایل را به ما بدهد.

مک‌ایلروی و هانت این ایده را در سال ۱۹۷۶ در قالب یک گزارش فنی با عنوان «الگوریتمی برای مقایسه‌ی تفاضلی فایل‌ها» (An Algorithm for Differential File Comparison) منتشر کردند. الگوریتمی که در این گزارش توصیف شده، بعدها به نام الگوریتم هانت-مک‌ایلروی (Hunt–McIlroy) شناخته شد، و پایه‌ی نسخه‌های بعدی diff، از جمله نسخه‌ی GNU که امروز روی تقریباً همه‌ی توزیع‌های لینوکس نصب است، قرار گرفت.

نکته‌ی جالب این‌جاست که این ایده هنوز هم زنده است. وقتی امروز دستور git diff را اجرا می‌کنید، یا در یک ابزار مرور کد آنلاین به تغییرات یک Pull Request نگاه می‌کنید، در پس‌زمینه، همان مفهوم بنیادینی در حال اجراست که در دهه‌ی ۱۹۷۰ در آزمایشگاه‌های بل ابداع شد؛ هرچند پیاده‌سازی‌های امروزی، مثل الگوریتم مایرز (Myers) که در Git استفاده می‌شود، بهینه‌تر و سریع‌تر شده‌اند.

### ۱.۲ diff چگونه تفاوت را پیدا می‌کند

شاید برایتان جالب باشد بدانید diff چطور تصمیم می‌گیرد کدام خط‌ها «تغییر کرده‌اند» و کدام خط‌ها «همان‌طور باقی مانده‌اند». پاسخ این پرسش به یک مسئله‌ی معروف در علوم کامپیوتر برمی‌گردد به نام «طولانی‌ترین زیردنباله‌ی مشترک» یا LCS (مخفف Longest Common Subsequence).

بدون این‌که وارد جزئیات ریاضی این مسئله شویم، ایده‌ی آن را می‌توانیم با یک مثال ساده توضیح دهیم. فرض کنید دو فایل متنی دارید که هرکدام چند خط دارند. diff، خط‌های هر فایل را مثل یک دنباله در نظر می‌گیرد، و به‌دنبال بلندترین زیرمجموعه‌ای از خط‌ها می‌گردد که در هر دو فایل، به همان ترتیب، مشترک هستند (لازم نیست این خط‌ها پشت‌سرهم باشند، فقط باید ترتیبشان حفظ شده باشد).

هر خطی که در این «بخش مشترک» بزرگ قرار نگیرد، به این معناست که یا از فایل اول حذف شده یا به فایل دوم اضافه شده است. به زبان ساده‌تر: diff دنبال این نیست که بگوید «خط اول با خط اول، خط دوم با خط دوم» مقایسه شود؛ بلکه دنبال بزرگ‌ترین بخش مشترکی می‌گردد که بین دو فایل باقی مانده، و هر چیزی خارج از آن بخش مشترک را به‌عنوان «تفاوت» گزارش می‌کند.

به همین دلیل است که وقتی مثلاً یک خط جدید در وسط یک فایل اضافه می‌کنید، diff معمولاً فقط همان یک خط جدید را به‌عنوان تفاوت گزارش می‌دهد، نه این‌که همه‌ی خط‌های بعدی را هم «تغییریافته» در نظر بگیرد، چون شماره‌شان جابه‌جا شده است. این هوشمندی، دقیقاً همان چیزی است که diff را از یک مقایسه‌ی ساده و خط‌به‌خط، به ابزاری واقعاً کاربردی تبدیل می‌کند.

الگوریتم‌های امروزی diff، مثل الگوریتم مایرز، در واقع همین مسئله را حل می‌کنند، اما با روش‌های سریع‌تر و کم‌حافظه‌تر، طوری که diff بتواند حتی فایل‌های بسیار بزرگ را در زمانی معقول پردازش کند.

### ۱.۳ نصب و بررسی نسخه‌ی diff

خبر خوب این است که در اکثر قریب به‌اتفاق توزیع‌های لینوکس، و همچنین در macOS، دستور diff از قبل نصب است، چون بخشی از بسته‌ی استاندارد GNU coreutils/diffutils محسوب می‌شود که همراه سیستم‌عامل عرضه می‌شود. برای این‌که مطمئن شوید diff روی سیستم شما نصب است و ببینید چه نسخه‌ای دارید، این دستور را در ترمینال اجرا کنید:

</div>

<div style="text-align:left;">

```
$ diff --version
```

### ۱.۴ اولین اجرای diff

بیایید با یک مثال بسیار ساده شروع کنیم. دو فایل متنی کوچک می‌سازیم تا رفتار پایه‌ی diff را ببینیم. ابتدا یک پوشه‌ی آزمایشی بسازید و به آن بروید:

</div>

<div style="text-align:left;">

```
$ mkdir ~/diff-test && cd ~/diff-test
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

حالا فایل اول را با این محتوا بسازید:

</div>

<div style="text-align:left;">

```
$ cat > file1.txt << 'EOF'
apple
banana
cherry
EOF
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

و فایل دوم را با یک تغییر کوچک:

</div>

<div style="text-align:left;">

```
$ cat > file2.txt << 'EOF'
apple
blueberry
cherry
EOF
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

همان‌طور که می‌بینید، تنها تفاوت این دو فایل در خط دوم است: «banana» در فایل اول به «blueberry» در فایل دوم تغییر کرده است. حالا بیایید این دو فایل را با diff مقایسه کنیم:

</div>

<div style="text-align:left;">

```
$ diff file1.txt file2.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی این‌طور خواهد بود:

</div>

<div style="text-align:left;">

```
2c2
< banana
---
> blueberry
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این خروجی، که به آن فرمت «عادی» یا normal گفته می‌شود (چون هیچ گزینه‌ی خاصی برای تغییر فرمت وارد نکردیم)، دقیقاً می‌گوید: «خط شماره‌ی ۲ فایل اول (c به معنای change یا تغییر) باید تبدیل شود به خط شماره‌ی ۲ فایل دوم». علامت < نشان‌دهنده‌ی محتوای فایل اول است، و علامت > نشان‌دهنده‌ی محتوای فایل دوم. در فصل بعدی، به‌طور کامل و با جزئیات بیشتر درباره‌ی این فرمت و فرمت‌های دیگر صحبت می‌کنیم.

### ۱.۵ کد بازگشتی (Exit Status) دستور diff

یک نکته‌ی مهم که خصوصاً هنگام استفاده از diff درون اسکریپت‌های شل به کارتان می‌آید، کد بازگشتی این دستور است. diff، برخلاف بسیاری از دستورهای دیگر که فقط ۰ (موفق) یا ۱ (خطا) برمی‌گردانند، سه حالت مختلف دارد:

- اگر دو فایل ورودی کاملاً یکسان باشند، diff هیچ خروجی‌ای چاپ نمی‌کند و کد بازگشتی آن ۰ خواهد بود.
- اگر دو فایل با هم تفاوت داشته باشند، diff تفاوت‌ها را چاپ می‌کند و کد بازگشتی آن ۱ خواهد بود.
- اگر مشکلی پیش بیاید، مثلاً یکی از فایل‌ها وجود نداشته باشد یا دسترسی لازم را نداشته باشید، کد بازگشتی ۲ خواهد بود.

این ویژگی خیلی مفید است، چون در یک اسکریپت شل می‌توانید بدون این‌که نیازی به تجزیه (parse) کردن متن خروجی diff داشته باشید، فقط با بررسی کد بازگشتی آن بفهمید دو فایل یکسان هستند یا نه. برای مثال:

</div>

<div style="text-align:left;">

```
$ diff -q config.old config.new > /dev/null
$ echo $?
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر خروجی این دستور عدد ۰ باشد، یعنی دو فایل یکسان بوده‌اند؛ اگر ۱ باشد، یعنی تفاوت داشته‌اند. (گزینه‌ی q- را در فصل بعدی به‌طور کامل توضیح می‌دهیم.)

### ۱.۶ چه چیزهایی را می‌توان با diff مقایسه کرد

تا این‌جا فقط دو فایل متنی ساده را مقایسه کردیم، اما diff قابلیت‌های بسیار بیشتری دارد که در فصل‌های بعدی به آن‌ها می‌پردازیم:

- می‌توان به‌جای دو فایل، دو پوشه‌ی کامل را با هم مقایسه کرد، حتی اگر داخل آن‌ها زیرپوشه‌های تودرتو باشند.
- می‌توان diff را وادار کرد تفاوت‌های ناشی از فاصله‌های خالی، بزرگی و کوچکی حروف، یا خطوط خالی را نادیده بگیرد.
- می‌توان خروجی diff را در قالب‌های گوناگون، از جمله فرمت آماده برای ساختن وصله (patch)، دریافت کرد.
- ابزار diff می‌تواند ورودی خود را از طریق stdin هم بگیرد، با استفاده از علامت -، که برای ترکیب کردن با دستورهای دیگر در یک خط لوله ```pipeline``` بسیار کاربردی است. برای مثال:

</div>

<div style="text-align:left;">

```
$ cat file2.txt | diff file1.txt -
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۱.۷ حالا چه؟

در این فصل، با تاریخچه‌ی diff، منطق کلی‌ای که بر اساس آن تفاوت‌ها را پیدا می‌کند، و ساده‌ترین شکل استفاده از آن آشنا شدید. همچنین یاد گرفتید چگونه نصب آن را بررسی کنید و کد بازگشتی آن را در اسکریپت‌ها به کار ببرید.

اما آنچه تا این‌جا دیدیم، تنها نوک کوه یخ است. خروجی diff می‌تواند به چند شکل کاملاً متفاوت نمایش داده شود، و انتخاب فرمت درست، بسته به این‌که می‌خواهید خروجی را خودتان بخوانید یا آن را به برنامه‌ی دیگری مثل patch بدهید، اهمیت زیادی دارد. در فصل بعدی، به‌طور کامل این فرمت‌ها را بررسی می‌کنیم.

### برای مرجع بعدی

| دستور | توضیح |
|---|---|
| diff file1 file2 | دو فایل را مقایسه می‌کند و تفاوت‌ها را در فرمت عادی (normal) نمایش می‌دهد. |
| diff --version | نسخه‌ی نصب‌شده‌ی diff را نمایش می‌دهد. |
| diff file1 - | فایل اول را با محتوای دریافتی از ورودی استاندارد (stdin) مقایسه می‌کند. |
| echo $؟ | کد بازگشتی آخرین دستور اجراشده را نمایش می‌دهد؛ برای diff می‌تواند ۰، ۱ یا ۲ باشد. |

</div>

<div dir="rtl" lang="fa" style="text-align: right;">

## فصل ۲

### <u>فرمت‌های خروجی diff</u>

در فصل قبل، یک بار خروجی ساده‌ی diff را دیدیم، اما گفتیم آن فقط یکی از چند فرمتی است که diff می‌تواند تفاوت‌ها را در آن نمایش دهد. در این فصل، هر یک از این فرمت‌ها را با جزئیات کامل بررسی می‌کنیم: فرمت عادی (normal)، فرمت متنی یا زمینه‌دار (context)، فرمت یکپارچه (unified)، و فرمت کنار هم (side-by-side). در پایان این فصل، می‌دانید هر فرمت را کجا و برای چه هدفی به کار ببرید.

### ۲.۱ فرمت عادی (Normal Format)

فرمت عادی، فرمت پیش‌فرض diff است؛ یعنی وقتی diff را بدون هیچ گزینه‌ای اجرا کنید، دقیقاً همین فرمت را می‌بینید. این فرمت، قدیمی‌ترین و ساده‌ترین شکل خروجی diff است، و اگرچه امروزه برای خواندن توسط انسان کمتر استفاده می‌شود، فهمیدن آن پایه‌ی فهمیدن فرمت‌های دیگر هم هست.

بیایید با همان دو فایل فصل قبل، اما این‌بار کمی پیچیده‌تر، کار کنیم. فایل lao را با این محتوا بسازید:

</div>

<div style="text-align:left;">

```
$ cat > lao.txt << 'EOF'
The Way that can be told of is not the eternal Way;
The name that can be named is not the eternal name.
The Nameless is the origin of Heaven and Earth;
The Named is the mother of all things.
Therefore let there always be non-being,
so we may see their subtlety,
And let there always be being,
so we may see their outcome.
The two are the same,
But after they are produced,
they have different names.
EOF
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

و فایل tzu را با این محتوا:

</div>

<div style="text-align:left;">

```
$ cat > tzu.txt << 'EOF'
The Nameless is the origin of Heaven and Earth;
The named is the mother of all things.

Therefore let there always be non-being,
so we may see their subtlety,
And let there always be being,
so we may see their outcome.
The two are the same,
But after they are produced,
they have different names.
They both may be called deep and profound.
Deeper and more profound,
The door of all subtleties!
EOF
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

حالا این دو فایل را مقایسه می‌کنیم:

</div>

<div style="text-align:left;">

```
$ diff lao.txt tzu.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی به این شکل خواهد بود:

</div>

<div style="text-align:left;">

```
1,2d0
< The Way that can be told of is not the eternal Way;
< The name that can be named is not the eternal name.
4c2,3
< The Named is the mother of all things.
---
> The named is the mother of all things.
>
11a11,13
> They both may be called deep and profound.
> Deeper and more profound,
> The door of all subtleties!
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این خروجی از چند «بخش» (که به آن‌ها hunk گفته می‌شود) تشکیل شده، و هر بخش با یک خط «دستور تغییر» شروع می‌شود. برای درک بهتر، بیایید فرمت این خط دستور را باز کنیم. هر خط دستور به این شکل است:

</div>

<div style="text-align:left;">

```
[شماره‌خط‌های فایل اول][حرف عملیات][شماره‌خط‌های فایل دوم]
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

سه نوع «حرف عملیات» وجود دارد:

- a (افزوده شدن — add): یعنی خط یا خط‌هایی به فایل دوم اضافه شده‌اند که در فایل اول وجود نداشتند.
- d (حذف شدن — delete): یعنی خط یا خط‌هایی از فایل اول حذف شده‌اند و در فایل دوم دیگر وجود ندارند.
- c (تغییر کردن — change): یعنی خط یا خط‌هایی از فایل اول با خط یا خط‌های دیگری در فایل دوم جایگزین شده‌اند.

با این تعریف، بیایید سه بخش خروجی بالا را یکی‌یکی معنا کنیم:

- ‪`1,2d0`‬ یعنی: خط‌های ۱ تا ۲ فایل اول (lao.txt) حذف شده‌اند؛ عدد ۰ بعد از d نشان می‌دهد این حذف، بعد از خط صفرم فایل دوم (یعنی از همان ابتدا) اتفاق افتاده است.
- ‪`4c2,3`‬ یعنی: خط ۴ فایل اول تغییر کرده و به خط‌های ۲ تا ۳ فایل دوم تبدیل شده است.
- ‪`11a11,13`‬ یعنی: بعد از خط ۱۱ فایل اول، سه خط جدید (خط‌های ۱۱ تا ۱۳ فایل دوم) اضافه شده‌اند.

بعد از هر خط دستور، محتوای واقعی خط‌ها می‌آید: خط‌هایی که با علامت ‪`<`‬ شروع می‌شوند، از فایل اول هستند، و خط‌هایی که با علامت ‪`>`‬ شروع می‌شوند، از فایل دوم. وقتی هم خط‌های ‪`<`‬ و هم خط‌های ‪`>`‬ در یک بخش وجود داشته باشند (یعنی در عملیات‌های نوع c)، این دو گروه با یک خط جداکننده‌ی سه‌خط‌تیره (‪`---`‬) از هم جدا می‌شوند.

عیب اصلی فرمت عادی این است که هیچ زمینه‌ای (context) اطراف تغییرات نشان نمی‌دهد؛ یعنی فقط خط‌هایی که واقعاً تغییر کرده‌اند را می‌بینید، بدون این‌که بدانید این تغییرات در کجای فایل و در چه فضایی رخ داده‌اند. به همین دلیل، برای فایل‌های بزرگ یا تغییرات پیچیده، خواندن این فرمت می‌تواند گیج‌کننده باشد.

### ۲.۲ فرمت زمینه‌دار (Context Format)

فرمت زمینه‌دار، که با گزینه‌ی ‪`-c`‬ یا ‪`--context`‬ (یا با حرف بزرگ ‪`-C`‬ برای مشخص کردن تعداد دقیق خطوط زمینه) فعال می‌شود، برخلاف فرمت عادی، چند خط قبل و بعد از تغییرات را هم نمایش می‌دهد. این کار خواندن خروجی را بسیار ساده‌تر می‌کند، چون تغییرات را در بافت واقعی خودشان می‌بینید.

بیایید همان دو فایل را این‌بار با گزینه‌ی ‪`-c`‬ مقایسه کنیم:

</div>

<div style="text-align:left;">

```
$ diff -c lao.txt tzu.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی چیزی شبیه به این خواهد بود:

</div>

<div style="text-align:left;">

```
* lao.txt	2026-01-15 10:00:00.000000000 +0330
--- tzu.txt	2026-01-15 10:05:00.000000000 +0330
*
* 1,11 
- The Way that can be told of is not the eternal Way;
- The name that can be named is not the eternal name.
  The Nameless is the origin of Heaven and Earth;
! The Named is the mother of all things.
  Therefore let there always be non-being,
   so we may see their subtlety,
  And let there always be being,
   so we may see their outcome.
  The two are the same,
  But after they are produced,
  they have different names.
--- 1,13 ----
  The Nameless is the origin of Heaven and Earth;
! The named is the mother of all things.
!
  Therefore let there always be non-being,
   so we may see their subtlety,
  And let there always be being,
   so we may see their outcome.
  The two are the same,
  But after they are produced,
  they have different names.
+ They both may be called deep and profound.
+ Deeper and more profound,
+ The door of all subtleties!
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

ساختار این خروجی به این شکل است:

نخست، دو خط بالای خروجی، نام و زمان آخرین تغییر (timestamp) هر دو فایل را نشان می‌دهند. فایل اول با سه ستاره (‪`*`‬) و فایل دوم با سه خط‌تیره (‪`---`‬) مشخص شده است. سپس یک خط جداکننده‌ی کامل از ستاره می‌آید، و بعد از آن، محتوای فایل اول در یک بخش (که با ‪`* [شماره‌خط‌ها] `‬ شروع می‌شود) و محتوای فایل دوم در بخش بعدی (که با ‪`--- [شماره‌خط‌ها] ----`‬ شروع می‌شود) نمایش داده می‌شوند.

در این خروجی، ابتدای هر خط یکی از این چهار علامت را دارد:

- علامتی وجود ندارد (فقط یک فاصله‌ی خالی): یعنی این خط بدون تغییر، در هر دو فایل مشترک است (خط زمینه).
- ‪`-`‬: یعنی این خط فقط در فایل اول وجود دارد و در فایل دوم حذف شده است.
- ‪`+`‬: یعنی این خط فقط در فایل دوم وجود دارد و تازه اضافه شده است.
- ‪`!`‬: یعنی این خط در هر دو فایل وجود دارد، اما محتوایش تغییر کرده است.

به‌طور پیش‌فرض، diff سه خط زمینه قبل و بعد از هر تغییر نشان می‌دهد. اگر بخواهید تعداد این خطوط را تغییر دهید، می‌توانید از ‪`-C`‬ به همراه یک عدد استفاده کنید:

</div>

<div style="text-align:left;">

```
$ diff -C 1 lao.txt tzu.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دستور فقط یک خط زمینه در اطراف هر تغییر نشان می‌دهد، که خروجی را کوتاه‌تر می‌کند.

فرمت زمینه‌دار، پیش‌تر فرمت رایج برای ساختن وصله (patch) بود، اما امروزه تقریباً به‌طور کامل جای خود را به فرمت یکپارچه، که در بخش بعد می‌بینیم، داده است. با این حال، ممکن است هنوز در برخی ابزارها یا پروژه‌های قدیمی‌تر با این فرمت روبه‌رو شوید.

### ۲.۳ فرمت یکپارچه (Unified Format)

فرمت یکپارچه، که با گزینه‌ی ‪`-u`‬ یا ‪`--unified`‬ فعال می‌شود، امروزه پرکاربردترین فرمت خروجی diff است. دلیل محبوبیت آن ساده است: تمام اطلاعاتی که فرمت زمینه‌دار دارد را حفظ می‌کند، اما به‌جای نمایش دو نسخه‌ی جداگانه از هر بخش (یکی برای فایل اول و یکی برای فایل دوم)، همه‌چیز را در یک بلوک واحد و فشرده‌تر نشان می‌دهد. به همین دلیل هم به آن «یکپارچه» یا Unified می‌گویند.

همین فرمت است که خروجی دستور git diff و بسیاری از ابزارهای مدرن مرور کد را تشکیل می‌دهد، پس آشنایی کامل با آن بسیار ارزشمند است.

بیایید همان دو فایل را این‌بار با ‪`-u`‬ مقایسه کنیم:

</div>

<div style="text-align:left;">

```
$ diff -u lao.txt tzu.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی به این شکل خواهد بود:

</div>

<div style="text-align:left;">

```
--- lao.txt	2026-01-15 10:00:00.000000000 +0330
+++ tzu.txt	2026-01-15 10:05:00.000000000 +0330
@@ -1,11 +1,13 @@
-The Way that can be told of is not the eternal Way;
-The name that can be named is not the eternal name.
 The Nameless is the origin of Heaven and Earth;
-The Named is the mother of all things.
+The named is the mother of all things.
+
 Therefore let there always be non-being,
  so we may see their subtlety,
 And let there always be being,
  so we may see their outcome.
 The two are the same,
 But after they are produced,
 they have different names.
+They both may be called deep and profound.
+Deeper and more profound,
+The door of all subtleties!
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

ساختار این خروجی این‌طور است: دو خط اول، نام و زمان تغییر هر دو فایل را نشان می‌دهند، این‌بار با علامت‌های ‪`---`‬ برای فایل اول و ‪`+++`‬ برای فایل دوم (دقیقاً برعکس چیزی که در فرمت زمینه‌دار دیدیم؛ آن‌جا ‪`*`‬ برای فایل اول و ‪`---`‬ برای فایل دوم بود).

بعد از آن، یک خط مهم می‌آید که به آن «سرآیند بخش» یا hunk header گفته می‌شود:

</div>

<div style="text-align:left;">

```
@@ -1,11 +1,13 @@
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این خط، محدوده‌ی خط‌هایی که در این بخش نمایش داده شده‌اند را در هر دو فایل مشخص می‌کند. فرمت آن به این شکل است: ‪`@@ -[خط شروع فایل اول],[تعداد خط از فایل اول] +[خط شروع فایل دوم],[تعداد خط از فایل دوم] @@`‬. پس ‪`-1,11`‬ یعنی این بخش از خط ۱ فایل اول شروع می‌شود و ۱۱ خط از آن فایل را دربردارد، و ‪`+1,13`‬ یعنی همین بخش، از خط ۱ فایل دوم شروع می‌شود اما ۱۳ خط از آن فایل را دربردارد (چون سه خط جدید اضافه شده‌اند).

در بدنه‌ی خروجی، هر خط با یکی از این سه علامت شروع می‌شود:

- فاصله‌ی خالی: خط بدون تغییر (زمینه)، مشترک در هر دو فایل.
- ‪`-`‬: خطی که فقط در فایل اول بود و حذف شده است.
- ‪`+`‬: خطی که تازه در فایل دوم اضافه شده است.

توجه کنید که در فرمت یکپارچه، برخلاف فرمت زمینه‌دار، دیگر خط‌های تغییریافته را دوبار (یک‌بار با ‪`!`‬ در بخش اول و یک‌بار در بخش دوم) نمی‌بینیم؛ به‌جای آن، خط قدیمی بلافاصله با علامت ‪`-`‬ و خط جدید با علامت ‪`+`‬، پشت‌سرهم نوشته می‌شوند. همین موضوع باعث می‌شود خروجی یکپارچه معمولاً کوتاه‌تر و فشرده‌تر از خروجی زمینه‌دار باشد، بدون این‌که هیچ اطلاعاتی از دست برود.

درست مثل فرمت زمینه‌دار، در فرمت یکپارچه هم می‌توانید تعداد خطوط زمینه را با گزینه‌ی ‪`-U`‬ به همراه یک عدد کنترل کنید:

</div>

<div style="text-align:left;">

```
$ diff -U 1 lao.txt tzu.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

یا حتی می‌توانید با ‪`-U 0`‬ زمینه را کاملاً حذف کنید، که خروجی را به کمترین حد ممکن می‌رساند و فقط دقیقاً خطوط تغییریافته را نشان می‌دهد.

یک نکته‌ی کاربردی دیگر، گزینه‌ی ‪`--label`‬ است که به شما اجازه می‌دهد به‌جای نام واقعی فایل و زمان تغییرش، برچسب دلخواه خودتان را در خط‌های ‪`---`‬ و ‪`+++`‬ نمایش دهید. این گزینه به‌ویژه هنگام ساختن وصله برای ارسال به دیگران مفید است:

</div>

<div style="text-align:left;">

```
$ diff -u --label "Old Version" --label "New Version" lao.txt tzu.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۲.۴ فرمت کنار هم (Side-by-Side)

فرمت کنار هم، که با گزینه‌ی ‪`-y`‬ یا ‪`--side-by-side`‬ فعال می‌شود، رویکردی کاملاً متفاوت دارد. به‌جای نمایش تغییرات به شکل خط‌های اضافه‌شده و حذف‌شده، دو فایل را در دو ستون کنار هم نمایش می‌دهد، طوری‌که هر خط از فایل اول دقیقاً روبه‌روی خط متناظرش از فایل دوم قرار می‌گیرد.

</div>

<div style="text-align:left;">

```
$ diff -y file1.txt file2.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی چیزی شبیه به این خواهد بود:

</div>

<div style="text-align:left;">

```
apple                                                          apple
banana                                                       | blueberry
cherry                                                         cherry
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

در وسط این دو ستون، یکی از این سه علامت ظاهر می‌شود:

- ‪`|`‬: نشان می‌دهد خط‌های دو طرف با هم فرق دارند.
- ‪`<`‬: نشان می‌دهد این خط فقط در فایل اول (ستون چپ) وجود دارد.
- ‪`>`‬: نشان می‌دهد این خط فقط در فایل دوم (ستون راست) وجود دارد.
- فاصله‌ی خالی: خط‌ها یکسان هستند.

این فرمت برای مقایسه‌ی سریع و بصری دو فایل نسبتاً کوتاه در ترمینال بسیار خوب است، چون می‌توانید هر دو نسخه را هم‌زمان ببینید. اما برای فایل‌های طولانی یا خط‌های بلند، این فرمت مشکل‌ساز می‌شود، چون عرض ترمینال محدود است. به‌طور پیش‌فرض، diff عرض خروجی را روی ۱۳۰ ستون تنظیم می‌کند، اما می‌توانید این مقدار را با گزینه‌ی ‪`-W`‬ تغییر دهید:

</div>

<div style="text-align:left;">

```
$ diff -y -W 200 file1.txt file2.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر عرض ترمینال شما کوچک‌تر از این مقدار باشد، خط‌ها به‌طور نامناسب می‌شکنند، پس بهتر است این مقدار را متناسب با عرض واقعی ترمینال خود تنظیم کنید.

دو گزینه‌ی تکمیلی هم برای این فرمت وجود دارند:

- ‪`--suppress-common-lines`‬: خط‌های مشترک (بدون تغییر) را از خروجی حذف می‌کند، تا فقط تفاوت‌ها دیده شوند.
- ‪`--left-column`‬: وقتی دو خط کاملاً یکسان هستند، به‌جای نمایش تکراری آن در هر دو ستون، فقط در ستون چپ نمایش می‌دهد.

### ۲.۵ فرمت‌های تخصصی‌تر: ed و RCS

علاوه بر چهار فرمت اصلی‌ای که دیدیم، diff دو فرمت دیگر هم دارد که کاربرد بسیار تخصصی‌تری دارند و امروزه کمتر با آن‌ها روبه‌رو می‌شوید، اما خوب است از وجودشان مطلع باشید.

فرمت ed، که با گزینه‌ی ‪`-e`‬ یا ‪`--ed`‬ فعال می‌شود، خروجی را طوری تولید می‌کند که مستقیماً قابل اجرا توسط ویرایشگر متنی خط‌فرمانی ed باشد. این یعنی اگر خروجی diff -e را در یک فایل ذخیره کنید و آن را به ed بدهید، فایل اول دقیقاً به فایل دوم تبدیل می‌شود. این فرمت یادگار روزهای اولیه‌ی یونیکس است، از زمانی که ed تنها ویرایشگر متنی موجود بود.

فرمت RCS، که با گزینه‌ی ‪`-n`‬ یا ‪`--rcs`‬ فعال می‌شود، شبیه فرمت عادی است اما برای استفاده توسط سیستم کنترل نسخه‌ی قدیمی RCS (مخفف Revision Control System) طراحی شده است. این سیستم پیش از Git و حتی پیش از CVS وجود داشت، و امروزه به‌ندرت مورد استفاده قرار می‌گیرد.

### ۲.۶ گزارش خلاصه به‌جای تفاوت کامل

گاهی اصلاً نمی‌خواهید بدانید دقیقاً چه چیزی تغییر کرده؛ فقط می‌خواهید بدانید آیا دو فایل با هم فرق دارند یا نه. برای همین منظور، دو گزینه‌ی ساده اما بسیار کاربردی وجود دارد:

گزینه‌ی ‪`-q`‬ یا ‪`--brief`‬ باعث می‌شود diff، به‌جای چاپ کامل تفاوت‌ها، فقط یک خط خلاصه چاپ کند که می‌گوید دو فایل با هم فرق دارند:

</div>

<div style="text-align:left;">

```
$ diff -q file1.txt file2.txt
Files file1.txt and file2.txt differ
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر فایل‌ها یکسان باشند، این گزینه هیچ خروجی‌ای تولید نمی‌کند (دقیقاً مثل حالت پیش‌فرض). برای این‌که وقتی فایل‌ها یکسان هستند هم پیامی ببینید، از گزینه‌ی ‪`-s`‬ یا ‪`--report-identical-files`‬ استفاده کنید:

</div>

<div style="text-align:left;">

```
$ diff -s file1.txt file1.txt
Files file1.txt and file1.txt are identical
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دو گزینه، به‌خصوص وقتی diff را در دل یک اسکریپت شل به کار می‌برید و فقط به یک پاسخ بله/خیر نیاز دارید، بسیار در وقت و پردازش صرفه‌جویی می‌کنند.

### ۲.۷ کدام فرمت را انتخاب کنیم؟

با این‌همه فرمت، شاید بپرسید کدام‌یک را باید در چه شرایطی استفاده کرد. جدول زیر یک راهنمای سریع برای انتخاب فرمت مناسب است:

| فرمت | گزینه | بهترین کاربرد |
|---|---|---|
| عادی (Normal) | بدون گزینه (پیش‌فرض) | خواندن ماشینی ساده یا اسکریپت‌های قدیمی؛ کمترین خوانایی برای انسان |
| زمینه‌دار (Context) | ‪-c‬ یا ‪-C NUM‬ | زمانی که با ابزارهای قدیمی یا پروژه‌های legacy کار می‌کنید |
| یکپارچه (Unified) | ‪-u‬ یا ‪-U NUM‬ | ساختن وصله، بررسی و مرور کد، استاندارد امروزی (مثل git diff) |
| کنار هم (Side-by-side) | ‪-y‬ | مقایسه‌ی بصری سریع دو فایل کوتاه در ترمینال |
| ed | ‪-e‬ | ساختن اسکریپت ویرایشی برای ویرایشگر ed |
| RCS | ‪-n‬ | سازگاری با سیستم کنترل نسخه‌ی قدیمی RCS |
| خلاصه | ‪-q‬ یا ‪-s‬ | فقط بررسی یکسان یا متفاوت بودن فایل‌ها، بدون جزئیات |

در عمل، برای اکثر کارهای روزمره، فرمت یکپارچه (‪-u‬) بهترین انتخاب است؛ هم خوانا است، هم فشرده، و هم استاندارد صنعتی امروز محسوب می‌شود. در فصل ۵ که درباره‌ی ساختن و اعمال وصله صحبت می‌کنیم، خواهید دید چرا این فرمت اهمیت ویژه‌ای دارد.

### ۲.۸ حالا چه؟

در این فصل، با همه‌ی فرمت‌های خروجی diff آشنا شدید و یاد گرفتید هرکدام را چگونه بخوانید. اما تا این‌جا فقط درباره‌ی *شکل* خروجی صحبت کردیم؛ در فصل بعد، به سراغ گزینه‌هایی می‌رویم که *محتوای* مقایسه را کنترل می‌کنند: چگونه فاصله‌های خالی را نادیده بگیرید، چگونه بزرگی و کوچکی حروف را نادیده بگیرید، و چگونه دقیقاً کنترل کنید diff به چه چیزهایی توجه کند و به چه چیزهایی بی‌توجه باشد.

### برای مرجع بعدی

| گزینه | توضیح |
|---|---|
| (بدون گزینه) | خروجی را در فرمت عادی (normal) نمایش می‌دهد. |
| ‪-c‬, ‪--context‬ | خروجی را در فرمت زمینه‌دار (context) با ۳ خط زمینه نمایش می‌دهد. |
| ‪-C NUM‬ | خروجی زمینه‌دار را با NUM خط زمینه نمایش می‌دهد. |
| ‪-u‬, ‪--unified‬ | خروجی را در فرمت یکپارچه (unified) با ۳ خط زمینه نمایش می‌دهد. |
| ‪-U NUM‬ | خروجی یکپارچه را با NUM خط زمینه نمایش می‌دهد. |
| ‪-y‬, ‪--side-by-side‬ | خروجی را در دو ستون کنار هم نمایش می‌دهد. |
| ‪-W NUM‬ | حداکثر عرض خروجی کنار هم را روی NUM ستون تنظیم می‌کند. |

| ‪-e‬, ‪--ed‬ | خروجی را به‌صورت یک اسکریپت قابل‌اجرا برای ویرایشگر ed تولید می‌کند. |
| ‪-n‬, ‪--rcs‬ | خروجی را در فرمت سازگار با سیستم RCS تولید می‌کند. |
| ‪-q‬, ‪--brief‬ | فقط گزارش می‌دهد که آیا فایل‌ها متفاوت‌اند یا نه، بدون نمایش جزئیات. |
| ‪-s‬, ‪--report-identical-files‬ | وقتی دو فایل یکسان‌اند، پیامی برای اطلاع نمایش می‌دهد. |
| ‪--label LABEL‬ | به‌جای نام فایل و زمان تغییر، برچسب دلخواه در سرآیند خروجی نمایش می‌دهد. |

</div>

## فصل ۳

### <u>کنترل رفتار diff با گزینه‌ها</u>

در فصل قبل دیدیم diff می‌تواند تفاوت‌ها را در قالب‌های گوناگون نمایش دهد، اما گاهی مسئله‌ی اصلی این نیست که تفاوت‌ها چگونه *نمایش* داده شوند، بلکه این است که اصلاً چه چیزی «تفاوت» محسوب شود. مثلاً آیا یک فاصله‌ی خالی اضافه در انتهای خط باید به‌عنوان تغییر گزارش شود؟ آیا تفاوت بین حروف بزرگ و کوچک مهم است؟ آیا خط‌های خالی اضافه‌شده اهمیت دارند؟ در این فصل، با گزینه‌هایی آشنا می‌شوید که به شما اجازه می‌دهند دقیقاً کنترل کنید diff به چه چیزهایی حساس باشد و از چه چیزهایی چشم‌پوشی کند.

### ۳.۱ نادیده گرفتن فاصله‌های خالی

یکی از رایج‌ترین مشکلاتی که در مقایسه‌ی فایل‌ها، به‌خصوص کد برنامه‌نویسی، پیش می‌آید، تفاوت‌های ظاهری ناشی از فاصله‌های خالی (space) و تب (tab) است. گاهی یک ویرایشگر متن، فاصله‌های انتهای خط را حذف می‌کند یا تورفتگی (indentation) را با روش دیگری می‌نویسد، بدون این‌که محتوای واقعی کد تغییر کرده باشد. diff چند گزینه دارد که دقیقاً برای همین موقعیت‌ها طراحی شده‌اند.

گزینه‌ی ‪-b‬ یا ‪--ignore-space-change‬ باعث می‌شود diff تغییر در *تعداد* فاصله‌های خالی پشت‌سرهم را نادیده بگیرد. یعنی اگر یک خط قبلاً یک فاصله بین دو کلمه داشت و حالا سه فاصله دارد، diff این را تغییر در نظر نمی‌گیرد؛ اما اگر یک خط اصلاً فاصله‌ای نداشت و حالا دارد، همچنان به‌عنوان تفاوت گزارش می‌شود.

</div>

<div style="text-align:left;">

```
$ diff -b old.txt new.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

گزینه‌ی ‪-w‬ یا ‪--ignore-all-space‬ یک قدم فراتر می‌رود و *تمام* فاصله‌های خالی را، در هر تعداد و هر جایی از خط، کاملاً نادیده می‌گیرد. با این گزینه، حتی اگر یک خط با هم چسبیده باشد و همان خط در فایل دیگر با فاصله‌های زیاد نوشته شده باشد، دو خط یکسان در نظر گرفته می‌شوند.

</div>

<div style="text-align:left;">

```
$ diff -w old.txt new.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

گزینه‌ی ‪-Z‬ یا ‪--ignore-trailing-space‬ فقط فاصله‌های خالی در *انتهای* خط را نادیده می‌گیرد. این گزینه به‌خصوص وقتی کاربردی است که یک ویرایشگر متن به‌طور خودکار فاصله‌های اضافی انتهای خط‌ها را پاک می‌کند و می‌خواهید این تغییرات جزئی در diff دیده نشوند.

و در نهایت، گزینه‌ی ‪-E‬ یا ‪--ignore-tab-expansion‬ تفاوت‌های ناشی از باز شدن (expand) کاراکتر تب به فاصله را نادیده می‌گیرد؛ یعنی اگر یک فایل از کاراکتر تب واقعی استفاده کند و فایل دیگر همان تورفتگی را با فاصله نوشته باشد، این گزینه کمک می‌کند این تفاوت ظاهری در گزارش دیده نشود.

جدول زیر تفاوت این چهار گزینه را خلاصه می‌کند:

| گزینه | رفتار |
|---|---|
| ‪-b‬ | تغییر در تعداد فاصله‌های پشت‌سرهم را نادیده می‌گیرد |
| ‪-w‬ | همه‌ی فاصله‌های خالی، هرجا که باشند، را کاملاً نادیده می‌گیرد |
| ‪-Z‬ | فقط فاصله‌های خالی انتهای خط را نادیده می‌گیرد |
| ‪-E‬ | تفاوت‌های ناشی از تبدیل تب به فاصله را نادیده می‌گیرد |

### ۳.۲ نادیده گرفتن بزرگی و کوچکی حروف

گاهی، به‌خصوص در فایل‌های پیکربندی یا متن‌های غیرحساس به بزرگی حروف، نمی‌خواهید diff بین «Hello» و «hello» فرقی بگذارد. گزینه‌ی ‪-i‬ یا ‪--ignore-case‬ دقیقاً همین کار را می‌کند: تفاوت‌های ناشی از بزرگ یا کوچک بودن حروف را در محتوای فایل‌ها نادیده می‌گیرد.

</div>

<div style="text-align:left;">

```
$ diff -i old.txt new.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

توجه داشته باشید این گزینه فقط روی *محتوای* فایل‌ها اثر دارد. اگر می‌خواهید هنگام مقایسه‌ی *پوشه‌ها*، بزرگی و کوچکی حروف در *نام فایل‌ها* را نیز نادیده بگیرید (که در فصل بعد با جزئیات بیشتر به مقایسه‌ی پوشه‌ها می‌پردازیم)، باید از گزینه‌ی جداگانه‌ی ‪--ignore-file-name-case‬ استفاده کنید. برعکسِ آن هم، یعنی ‪--no-ignore-file-name-case‬، وجود دارد که به‌طور صریح می‌گوید بزرگی و کوچکی حروف در نام فایل‌ها باید در نظر گرفته شود (که معمولاً همان رفتار پیش‌فرض است).

### ۳.۳ نادیده گرفتن خطوط خالی

اگر تنها تفاوت بین دو نسخه از یک فایل، اضافه یا کم شدن چند خط خالی باشد (مثلاً برای خوانایی بیشتر کد)، ممکن است نخواهید این موارد را به‌عنوان تغییر واقعی ببینید. گزینه‌ی ‪-B‬ یا ‪--ignore-blank-lines‬ دقیقاً برای همین موقعیت طراحی شده است: تغییراتی که فقط شامل اضافه یا کم شدن خطوط کاملاً خالی هستند را نادیده می‌گیرد.

</div>

<div style="text-align:left;">

```
$ diff -B old.txt new.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

دقت کنید این گزینه فقط خط‌هایی را نادیده می‌گیرد که *کاملاً خالی* باشند؛ اگر یک خط فقط شامل چند فاصله باشد (نه کاملاً خالی)، ممکن است لازم باشد آن را همراه با گزینه‌ی ‪-w‬ ترکیب کنید تا نتیجه‌ی دلخواه را بگیرید.

### ۳.۴ نادیده گرفتن خطوطی که با یک الگو مطابقت دارند

گاهی می‌خواهید تغییراتی که فقط مربوط به خطوط خاصی هستند، مثلاً خطوطی که شامل تاریخ یا شماره‌ی نسخه‌اند، در خروجی diff نادیده گرفته شوند. گزینه‌ی ‪-I‬ یا ‪--ignore-matching-lines=RE‬ به شما اجازه می‌دهد یک عبارت باقاعده (regular expression) وارد کنید؛ اگر *همه‌ی* خطوطی که در یک بخش (hunk) تغییر کرده‌اند با این الگو مطابقت داشته باشند، آن بخش کلاً از خروجی حذف می‌شود.

برای مثال، فرض کنید فایل‌های شما خطی شامل تاریخ ساخت دارند، مثل «Generated on: 2026-01-15»، و می‌خواهید تغییر در همین خط را در diff نادیده بگیرید:

</div>

<div style="text-align:left;">

```
$ diff -I '^Generated on:' old.txt new.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

نکته‌ی مهم این‌جاست که این گزینه فقط زمانی یک بخش تغییر را کاملاً حذف می‌کند که *تمام* خط‌های تغییریافته‌ی آن بخش با الگو مطابقت داشته باشند. اگر یک بخش شامل هم خط منطبق با الگو و هم خط دیگری باشد، کل بخش همچنان نمایش داده می‌شود. برای استفاده از چند الگوی مختلف هم‌زمان، می‌توانید این گزینه را چندین بار تکرار کنید.

### ۳.۵ رفتار diff با فایل‌های متنی و باینری

به‌طور پیش‌فرض، diff سعی می‌کند تشخیص دهد آیا یک فایل، فایل متنی است یا باینری. اگر تشخیص دهد فایلی باینری است، به‌جای نمایش خط‌به‌خط تفاوت‌ها، فقط پیامی ساده مثل این چاپ می‌کند:

</div>

<div style="text-align:left;">

```
Binary files file1.bin and file2.bin differ
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اما گاهی این تشخیص خودکار درست عمل نمی‌کند، مثلاً یک فایل متنی حاوی کاراکترهای خاص یا کدگذاری غیرمعمول است و diff اشتباهاً آن را باینری تشخیص می‌دهد. گزینه‌ی ‪-a‬ یا ‪--text‬ به diff می‌گوید که با *همه‌ی* فایل‌ها، حتی اگر شبیه باینری به نظر برسند، همچون فایل متنی رفتار کند و خط‌به‌خط مقایسه‌شان کند.

</div>

<div style="text-align:left;">

```
$ diff -a file1 file2
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

باید مراقب استفاده از این گزینه با فایل‌های واقعاً باینری بود، چون خروجی diff در آن صورت ممکن است بی‌معنی یا حتی باعث بروز کاراکترهای عجیب در ترمینال شما شود.

یک گزینه‌ی کوچک‌تر و مرتبط، ‪--strip-trailing-cr‬ است که کاراکتر بازگشت به ابتدای خط (carriage return یا CR) را از انتهای هر خط ورودی حذف می‌کند، پیش از آن‌که مقایسه انجام شود. این گزینه به‌ویژه وقتی کاربردی است که یکی از فایل‌ها با انتهای خط سبک ویندوز (CRLF) ذخیره شده و دیگری با سبک یونیکس/لینوکس (LF)؛ بدون این گزینه، diff این تفاوت انتهای خط را به‌عنوان تغییر در *همه‌ی* خطوط فایل گزارش می‌دهد، که معمولاً چیزی نیست که واقعاً به آن اهمیت بدهید.

### ۳.۶ کنترل دقت و سرعت الگوریتم

در فصل ۱ درباره‌ی این صحبت کردیم که diff از الگوریتمی برای پیدا کردن طولانی‌ترین زیردنباله‌ی مشترک استفاده می‌کند. این الگوریتم، مثل بسیاری از الگوریتم‌های بهینه‌سازی، گاهی بین «سریع بودن» و «پیدا کردن کوچک‌ترین تفاوت ممکن» یک مصالحه (trade-off) برقرار می‌کند. دو گزینه وجود دارند که به شما اجازه می‌دهند این مصالحه را کنترل کنید.

گزینه‌ی ‪-d‬ یا ‪--minimal‬ به diff می‌گوید تلاش بیشتری برای پیدا کردن کوچک‌ترین مجموعه‌ی ممکن از تغییرات بکند. معمولاً diff، برای صرفه‌جویی در زمان پردازش، از یک روش تقریبی (heuristic) استفاده می‌کند که همیشه کوچک‌ترین تغییر ممکن را پیدا نمی‌کند، بلکه یک تغییر «به‌اندازه‌ی کافی کوچک» را در زمان معقولی برمی‌گرداند. با فعال کردن ‪-d‬، از diff می‌خواهید صرف‌نظر از زمان بیشتری که طول می‌کشد، دقیق‌ترین و کوچک‌ترین خروجی را پیدا کند. برای فایل‌های کوچک تفاوت محسوسی نمی‌بینید، اما برای فایل‌های بزرگ و پیچیده، این گزینه می‌تواند زمان پردازش را به‌طور قابل‌توجهی افزایش دهد.

</div>

<div style="text-align:left;">

```
$ diff -d file1 file2
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

در طرف مقابل، گزینه‌ی ‪--speed-large-files‬ به diff می‌گوید فرض کند با فایل‌های بزرگ و دارای تغییرات پراکنده‌ی زیاد سروکار دارد، و بر اساس این فرض، الگوریتمی سریع‌تر (اما احتمالاً کمی کمتر دقیق) به کار ببرد. این گزینه برای فایل‌های بسیار بزرگ، مثل فایل‌های لاگ یا خروجی داده‌های حجیم، می‌تواند سرعت پردازش را به‌شکل چشمگیری بهبود دهد.

گزینه‌ی دیگری هم به نام ‪--horizon-lines=NUM‬ وجود دارد که در موقعیت‌های تخصصی‌تر به کار می‌آید: تعداد خطوطی از پیشوند و پسوند مشترک بین دو فایل را که باید در حافظه نگه‌داشته شوند، مشخص می‌کند. این گزینه معمولاً فقط زمانی لازم می‌شود که با ابزارهای دیگری که خروجی diff را پردازش می‌کنند (مثل patch) و به این «افق» (horizon) نیاز دارند، کار می‌کنید.

### ۳.۷ کار کردن با تب‌ها و ستون‌بندی خروجی

diff چند گزینه هم برای کنترل ظاهر بصری خروجی، به‌خصوص در ارتباط با کاراکتر تب، دارد.

گزینه‌ی ‪-t‬ یا ‪--expand-tabs‬ باعث می‌شود diff، هنگام نمایش خروجی، کاراکترهای تب را به فاصله‌ی معادلشان تبدیل کند. این کار به‌خصوص وقتی مفید است که علامت‌های ابتدای خط (مثل ‪<‬، ‪>‬، ‪+‬ یا ‪-‬) باعث می‌شوند تورفتگی خطوط به‌هم بریزد؛ با تبدیل تب‌ها به فاصله، ستون‌بندی درست‌تر حفظ می‌شود.

گزینه‌ی ‪-T‬ یا ‪--initial-tab‬ یک کاراکتر تب واقعی، به‌جای فاصله، قبل از هر خط خروجی اضافه می‌کند تا خطوط بهتر با هم تراز شوند؛ این خصوصاً برای فرمت‌های context و unified، که یک یا دو کاراکتر در ابتدای خط دارند، مفید است.

گزینه‌ی ‪--tabsize=NUM‬ هم اندازه‌ی هر توقف‌گاه تب (tab stop) را، که به‌طور پیش‌فرض ۸ ستون است، تغییر می‌دهد.

و در نهایت، ‪--suppress-blank-empty‬ باعث می‌شود diff، پیش از خطوط کاملاً خالی در خروجی، از قرار دادن فاصله یا تب خودداری کند؛ این گزینه برای زمانی مفید است که می‌خواهید خروجی diff را با ابزارهایی که به فاصله‌ی اضافی حساس هستند ترکیب کنید.

### ۳.۸ نمایش زمینه‌ی برنامه‌نویسی (فقط برای کد C)

اگر روی کد زبان C کار می‌کنید، دو گزینه‌ی جالب وجود دارند که به شما کمک می‌کنند بفهمید هر تغییر داخل کدام تابع رخ داده است.

گزینه‌ی ‪-p‬ یا ‪--show-c-function‬، در فرمت‌های context و unified، نام آخرین تابع C ای که پیش از هر بخش تغییریافته ظاهر شده را در سرآیند همان بخش نشان می‌دهد. این باعث می‌شود، حتی بدون باز کردن کل فایل، بلافاصله بفهمید یک تغییر مربوط به کدام تابع بوده است.

گزینه‌ی عمومی‌تر ‪-F RE‬ یا ‪--show-function-line=RE‬ همین ایده را گسترش می‌دهد: به‌جای این‌که فقط دنبال تعریف تابع C بگردد، شما یک عبارت باقاعده‌ی دلخواه می‌دهید، و diff نزدیک‌ترین خط پیش از هر تغییر که با آن الگو مطابقت دارد را در سرآیند بخش نشان می‌دهد. این گزینه برای زبان‌های دیگر یا برای دنبال کردن هر ساختار دیگری غیر از تابع (مثل تعریف کلاس یا بخش‌بندی‌های یک فایل پیکربندی) کاربرد دارد.

### ۳.۹ صفحه‌بندی خروجی طولانی

اگر diff را روی دو فایل بزرگ اجرا کنید، ممکن است خروجی آن‌قدر طولانی شود که به‌سختی بتوانید آن را در ترمینال دنبال کنید. گزینه‌ی ‪-l‬ یا ‪--paginate‬ خروجی diff را از طریق دستور pr عبور می‌دهد، که آن را به صفحات مجزا با سرصفحه (header) تقسیم می‌کند؛ این کار برای چاپ کردن خروجی یا مرور آن به‌صورت صفحه‌به‌صفحه مفید است.

</div>

<div style="text-align:left;">

```
$ diff -l file1 file2
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

در عمل، امروزه بیشتر افراد ترجیح می‌دهند به‌جای این گزینه، خروجی diff را مستقیماً به دستور less لوله (pipe) کنند، که امکانات جست‌وجو و پیمایش بهتری می‌دهد:

</div>

<div style="text-align:left;">

```
$ diff -u file1 file2 | less
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۳.۱۰ رنگی کردن خروجی

نسخه‌های نسبتاً جدید GNU diff، امکان رنگی کردن خروجی را هم اضافه کرده‌اند، که خواندن تفاوت‌ها را در ترمینال بسیار ساده‌تر می‌کند. گزینه‌ی ‪--color[=WHEN]‬ این قابلیت را کنترل می‌کند. مقدار WHEN می‌تواند یکی از این سه باشد:

- never: هرگز رنگی نکن (رفتار پیش‌فرض در بسیاری نسخه‌ها، به‌خصوص وقتی خروجی به فایل یا لوله هدایت می‌شود).
- always: همیشه رنگی کن، حتی اگر خروجی به فایل هدایت شود.
- auto: فقط وقتی خروجی مستقیماً به یک ترمینال نمایش داده می‌شود رنگی کن (اگر فقط ‪--color‬ بدون مقدار بنویسید، همین حالت انتخاب می‌شود).

</div>

<div style="text-align:left;">

```
$ diff --color=auto -u file1.txt file2.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

با رنگی شدن خروجی، معمولاً خطوط حذف‌شده به رنگ قرمز و خطوط اضافه‌شده به رنگ سبز نمایش داده می‌شوند، دقیقاً همان قراردادی که در ابزارهایی مثل git diff هم می‌بینید.

اگر بخواهید پالت رنگی پیش‌فرض را نیز سفارشی کنید، می‌توانید از گزینه‌ی ‪--palette=PALETTE‬ استفاده کنید، که مقدار آن فهرستی جدا شده با دونقطه از قابلیت‌های terminfo است.

### ۳.۱۱ ترکیب کردن گزینه‌ها

نکته‌ی خوب درباره‌ی گزینه‌های diff این است که اکثر آن‌ها را می‌توان با هم ترکیب کرد. برای مثال، یک ترکیب بسیار رایج و کاربردی برای مقایسه‌ی کد برنامه‌نویسی، نادیده گرفتن فاصله‌های خالی همراه با فرمت یکپارچه و رنگی است:

</div>

<div style="text-align:left;">

```
$ diff -u -w --color=auto old_code.py new_code.py
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

یا اگر فقط می‌خواهید بدانید آیا دو فایل پیکربندی، با چشم‌پوشی از فاصله‌ها و بزرگی/کوچکی حروف، واقعاً متفاوت هستند یا نه:

</div>

<div style="text-align:left;">

```
$ diff -q -b -i config1.conf config2.conf
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

آشنایی با این گزینه‌ها و توانایی ترکیب کردنشان، دقیقاً همان چیزی است که diff را از یک ابزار ساده به یک ابزار بسیار انعطاف‌پذیر برای کارهای روزمره تبدیل می‌کند.

### ۳.۱۲ حالا چه؟

در این فصل، با ده‌ها گزینه‌ای آشنا شدید که به شما اجازه می‌دهند دقیقاً کنترل کنید diff به چه چیزهایی توجه کند: فاصله‌های خالی، بزرگی و کوچکی حروف، خطوط خالی، الگوهای خاص، و حتی دقت و سرعت الگوریتم مقایسه. تا این‌جا همه‌ی این گزینه‌ها را روی مقایسه‌ی دو *فایل* دیدیم. اما همان‌طور که در فصل ۱ اشاره کردیم، diff می‌تواند دو *پوشه‌ی کامل* را هم با هم مقایسه کند. در فصل بعد، دقیقاً همین موضوع را بررسی می‌کنیم.

## فصل ۴

### <u>مقایسه‌ی پوشه‌ها و مجموعه فایل‌ها</u>

تا این‌جا، همیشه دو فایل تنها را با هم مقایسه کردیم. اما در دنیای واقعی، اغلب لازم است دو نسخه‌ی کامل از یک پروژه، یک پوشه‌ی پیکربندی، یا حتی یک نسخه‌ی پشتیبان کامل را با نسخه‌ی فعلی‌شان مقایسه کنید. خبر خوب این است که diff می‌تواند دقیقاً همین کار را انجام دهد: نه‌فقط دو فایل، بلکه دو پوشه‌ی کامل، با هر تعداد زیرپوشه‌ی تودرتو که داشته باشند.

### ۴.۱ مقایسه‌ی سطحی دو پوشه

ساده‌ترین حالت، وقتی است که دو پوشه را مستقیماً به diff بدهید، بدون هیچ گزینه‌ی خاصی:

</div>

<div style="text-align:left;">

```
$ diff dir1 dir2
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

در این حالت، diff فقط فایل‌هایی که *مستقیماً* داخل این دو پوشه هستند را بررسی می‌کند (نه زیرپوشه‌ها را). برای هر فایلی که در هر دو پوشه با همان نام وجود دارد، محتوایش را مثل قبل مقایسه می‌کند و تفاوت‌ها را نشان می‌دهد. برای فایل‌هایی که فقط در یکی از دو پوشه وجود دارند، پیامی مثل این چاپ می‌کند:

</div>

<div style="text-align:left;">

```
Only in dir1: file1.txt
Only in dir2: file2.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

و اگر یکی از این «فایل‌ها» در واقع یک زیرپوشه باشد که در طرف مقابل زیرپوشه‌ی مشابهی ندارد، همان پیام «Only in» را برای آن زیرپوشه هم می‌بینید، بدون این‌که وارد محتوای آن شود.

اگر دو پوشه شامل زیرپوشه‌های مشترک باشند، diff به‌طور پیش‌فرض وارد آن‌ها نمی‌شود؛ فقط اعلام می‌کند که آن مسیر یک پوشه است و متفاوت است:

</div>

<div style="text-align:left;">

```
Common subdirectories: dir1/subdir and dir2/subdir
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

برای این‌که واقعاً وارد این زیرپوشه‌ها هم بشود و محتوای آن‌ها را هم مقایسه کند، به گزینه‌ی بعدی نیاز داریم.

### ۴.۲ مقایسه‌ی بازگشتی (Recursive)

گزینه‌ی ‪-r‬ یا ‪--recursive‬ به diff می‌گوید وارد هر زیرپوشه‌ای شود و آن را هم، تا هر عمقی که لازم باشد، با زیرپوشه‌ی متناظرش مقایسه کند. این یکی از پرکاربردترین گزینه‌ها هنگام کار با پوشه‌هاست:

</div>

<div style="text-align:left;">

```
$ diff -r dir1 dir2
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی چیزی شبیه به این خواهد بود:

</div>

<div style="text-align:left;">

```
Only in dir1: file1.txt
Only in dir2: file2.txt
diff -r dir1/subdir/config.txt dir2/subdir/config.txt
3c3
< timeout = 30
---
> timeout = 60
Only in dir1/subdir: old_notes.md
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

همان‌طور که می‌بینید، diff هر زیرپوشه‌ی مشترک را باز کرده، فایل‌های داخلش را یکی‌یکی مقایسه کرده، و فایل‌هایی که فقط در یک طرف وجود دارند را هم گزارش کرده است.

اگر فقط بخواهید بدانید *کدام* فایل‌ها با هم فرق دارند، بدون دیدن جزئیات دقیق تفاوت درون هر فایل، می‌توانید ‪-r‬ را با ‪-q‬ (که در فصل ۲ دیدیم) ترکیب کنید:

</div>

<div style="text-align:left;">

```
$ diff -rq dir1 dir2
```
</div>

<div style="text-align:left;">

```
Files dir1/readme.md and dir2/readme.md differ
Only in dir2: newfile.txt
Only in dir1: oldfile.txt
Files dir1/src/main.py and dir2/src/main.py differ
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این ترکیب، یکی از رایج‌ترین دستورهایی است که در عمل برای مقایسه‌ی سریع دو نسخه از یک پروژه یا دو نسخه‌ی پشتیبان استفاده می‌شود، چون یک خلاصه‌ی سریع و خوانا از همه‌ی تفاوت‌ها می‌دهد بدون این‌که صفحه را پر از جزئیات کند.

### ۴.۳ کنترل عمق و شروع مقایسه

اگر پوشه‌ی بزرگی دارید و پیش‌تر شروع به مقایسه کرده بودید اما کار نیمه‌تمام ماند، گزینه‌ی ‪-S FILE‬ یا ‪--starting-file=FILE‬ به شما اجازه می‌دهد مقایسه را از یک فایل مشخص در سطح بالای پوشه به بعد (به ترتیب الفبایی) از سر بگیرید، بدون این‌که فایل‌های پیش از آن دوباره بررسی شوند:

</div>

<div style="text-align:left;">

```
$ diff -r -S readme.md dir1 dir2
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۴.۴ رفتار با فایل‌هایی که فقط در یک طرف وجود دارند

به‌طور پیش‌فرض، وقتی فایلی فقط در یکی از دو پوشه وجود داشته باشد، diff فقط پیام «Only in» را چاپ می‌کند و وارد محتوای آن فایل نمی‌شود. اما گاهی می‌خواهید ببینید محتوای کامل آن فایل، به‌عنوان یک «تفاوت کامل» نسبت به یک فایل خالی، چگونه است. این دقیقاً کاربردی است که هنگام ساختن وصله (patch) برای فایل‌های تازه اضافه‌شده لازم می‌شود، موضوعی که در فصل بعد به آن می‌پردازیم.

گزینه‌ی ‪-N‬ یا ‪--new-file‬ به diff می‌گوید، هر وقت فایلی فقط در یکی از دو طرف حضور دارد، طرف دیگر را «یک فایل خالی» در نظر بگیرد و تفاوت کامل را نشان دهد:

</div>

<div style="text-align:left;">

```
$ diff -rN dir1 dir2
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

با این گزینه، به‌جای پیام «Only in dir2: newfile.txt»، خروجی کامل یک diff می‌بینید که نشان می‌دهد *همه‌ی* خطوط newfile.txt تازه اضافه شده‌اند (چون طرف مقابل را خالی در نظر گرفته است).

گزینه‌ی مشابه دیگری هم به نام ‪--unidirectional-new-file‬ وجود دارد. تفاوتش با ‪-N‬ این است که فقط فایل‌هایی که در *فایل دوم* (پوشه‌ی جدیدتر) وجود دارند اما در فایل اول نیستند را به همین شکل «تفاوت کامل نسبت به خالی» نشان می‌دهد؛ اما فایل‌هایی که فقط در پوشه‌ی *اول* هستند (یعنی در نسخه‌ی جدید حذف شده‌اند) را نادیده می‌گیرد. این گزینه معمولاً برای ساختن وصله‌های کوچک‌تر به کار می‌رود، وقتی می‌خواهید فقط تغییرات و افزوده‌شده‌ها را نشان دهید، بدون توجه به فایل‌های حذف‌شده.

### ۴.۵ حذف فایل‌ها و الگوها از مقایسه

وقتی با پوشه‌های بزرگ، به‌خصوص پروژه‌های نرم‌افزاری، کار می‌کنید، معمولاً فایل‌ها یا پوشه‌هایی هستند که اصلاً نمی‌خواهید در مقایسه دخالت داده شوند: فایل‌های لاگ، پوشه‌ی کنترل نسخه (مثل ‪.git‬)، فایل‌های موقت، یا خروجی‌های کامپایل‌شده.

گزینه‌ی ‪-x PATTERN‬ یا ‪--exclude=PATTERN‬ به شما اجازه می‌دهد فایل‌ها یا پوشه‌هایی که با یک الگوی مشخص مطابقت دارند را از مقایسه کنار بگذارید:

</div>

<div style="text-align:left;">

```
$ diff -rq -x '*.log' dir1 dir2
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دستور همه‌ی فایل‌های با پسوند ‪.log‬ را از مقایسه حذف می‌کند. می‌توانید این گزینه را چندین بار تکرار کنید تا چند الگو را هم‌زمان مستثنا کنید:

</div>

<div style="text-align:left;">

```
$ diff -rq -x '*.log' -x '*.tmp' -x '.git' dir1 dir2
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر تعداد الگوهایی که می‌خواهید حذف کنید زیاد باشد، نوشتن همه‌شان در خط فرمان دست‌وپاگیر می‌شود. برای این موقعیت، گزینه‌ی ‪-X FILE‬ یا ‪--exclude-from=FILE‬ وجود دارد که الگوها را از یک فایل متنی می‌خواند (هر الگو در یک خط جداگانه):

</div>

<div style="text-align:left;">

```
$ cat > ignore-patterns.txt << 'EOF'
*.log
*.tmp
.git
node_modules
EOF
$ diff -rq -X ignore-patterns.txt dir1 dir2
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این روش، به‌خصوص وقتی همان مجموعه‌ی الگوها را بارها استفاده می‌کنید (مثلاً در یک اسکریپت پشتیبان‌گیری)، خیلی تمیزتر و قابل‌نگهداری‌تر است.

### ۴.۶ نادیده گرفتن بزرگی و کوچکی حروف در نام فایل‌ها

همان‌طور که در فصل قبل اشاره کردیم، گزینه‌ی ‪--ignore-file-name-case‬ مخصوص مقایسه‌ی پوشه‌هاست. اگر دو پوشه، به‌خاطر تفاوت در سیستم فایل مبدأ (مثلاً یکی از یک سیستم ویندوزی که به بزرگی و کوچکی حروف حساس نیست کپی شده)، فایل‌هایی با نام‌های «Report.txt» و «report.txt» داشته باشند، این گزینه به diff می‌گوید این دو را همان یک فایل در نظر بگیرد و محتوایشان را مقایسه کند:

</div>

<div style="text-align:left;">

```
$ diff -r --ignore-file-name-case dir1 dir2
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر بخواهید به‌طور صریح رفتار پیش‌فرض (حساس به بزرگی/کوچکی حروف) را اعمال کنید، از ‪--no-ignore-file-name-case‬ استفاده می‌کنید.

### ۴.۷ دنبال کردن یا نکردن لینک‌های نمادین

اگر پوشه‌های شما شامل لینک‌های نمادین (symbolic link) باشند، رفتار پیش‌فرض diff این است که این لینک‌ها را دنبال کند و محتوای فایل واقعی که به آن اشاره می‌کنند را مقایسه کند. اگر نمی‌خواهید این اتفاق بیفتد، و می‌خواهید خود لینک‌ها (و نه فایل‌های مقصدشان) با هم مقایسه شوند، از گزینه‌ی ‪--no-dereference‬ استفاده کنید:

</div>

<div style="text-align:left;">

```
$ diff -r --no-dereference dir1 dir2
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این گزینه به‌خصوص زمانی مهم است که در حال مقایسه‌ی ساختار یک پوشه هستید (نه محتوای واقعی فایل‌هایی که لینک‌ها به آن‌ها اشاره می‌کنند)، مثلاً برای بررسی این‌که آیا لینک‌های نمادین درست ساخته شده‌اند یا نه.

### ۴.۸ مقایسه‌ی یک فایل با چند فایل دیگر

دو گزینه‌ی کمتر شناخته‌شده اما بسیار کاربردی، ‪--from-file=FILE1‬ و ‪--to-file=FILE2‬ هستند. این‌ها به شما اجازه می‌دهند بدون محدودیت‌های معمول diff (که یا باید دو فایل، یا دو پوشه، یا یک فایل و یک پوشه بدهید)، یک فایل ثابت را با *چند* فایل یا عملوند دیگر مقایسه کنید.

برای مثال، فرض کنید می‌خواهید یک الگوی مرجع (template.txt) را با چند فایل پیکربندی مختلف مقایسه کنید:

</div>

<div style="text-align:left;">

```
$ diff --from-file=template.txt config1.txt config2.txt config3.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دستور، الگو را جداگانه با هر سه فایل مقایسه می‌کند و برای هر کدام یک بخش خروجی جدا نشان می‌دهد. برعکس آن هم با ‪--to-file‬ ممکن است: مقایسه‌ی چند فایل مبدأ با یک فایل مقصد ثابت.

### ۴.۹ یک مثال کامل و واقعی

بیایید همه‌ی این‌ها را در یک مثال ترکیب کنیم. فرض کنید دو نسخه از یک پروژه‌ی کوچک وب دارید، در پوشه‌های project-v1 و project-v2، و می‌خواهید بدانید دقیقاً چه فایل‌هایی تغییر کرده‌اند، بدون احتساب فایل‌های لاگ، پوشه‌ی وابستگی‌ها (مثل node_modules)، و بدون حساسیت به فاصله‌های خالی:

</div>

<div style="text-align:left;">

```
$ diff -rq -w \
    -x '*.log' \
    -x 'node_modules' \
    -x '.git' \
    project-v1 project-v2
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی این دستور، یک فهرست تمیز و خوانا از تمام فایل‌هایی است که واقعاً محتوایشان تغییر کرده، بدون هیچ نویز اضافه‌ای:

</div>

<div style="text-align:left;">

```
Files project-v1/index.html and project-v2/index.html differ
Only in project-v2/src: newComponent.js
Files project-v1/package.json and project-v2/package.json differ
Only in project-v1: deprecated-script.sh
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

از این‌جا، اگر بخواهید جزئیات دقیق تغییر در یک فایل مشخص را ببینید، می‌توانید همان دو فایل را جداگانه، این‌بار با فرمت یکپارچه، مقایسه کنید:

</div>

<div style="text-align:left;">

```
$ diff -u project-v1/package.json project-v2/package.json
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۴.۱۰ حالا چه؟

در این فصل دیدید diff چگونه می‌تواند نه‌فقط دو فایل، بلکه دو ساختار کامل از پوشه‌ها و زیرپوشه‌ها را با هم مقایسه کند، چگونه فایل‌ها و الگوهای خاص را از این مقایسه کنار بگذارید، و چگونه رفتار آن را با لینک‌های نمادین و فایل‌های یک‌طرفه کنترل کنید.

تا این‌جا، diff را عمدتاً به‌عنوان ابزاری برای *دیدن* تفاوت‌ها استفاده کرده‌ایم. اما یکی از قدرتمندترین کاربردهای diff این است که خروجی آن می‌تواند به یک «وصله» (patch) تبدیل شود؛ یعنی فایلی که توصیف می‌کند چگونه یک فایل یا مجموعه‌ای از فایل‌ها را از حالت قدیم به حالت جدید تبدیل کنیم، بدون این‌که نیاز باشد کل فایل جدید را جابه‌جا کنیم. در فصل بعد، دقیقاً به همین موضوع می‌پردازیم.

### برای مرجع بعدی

| گزینه | توضیح |
|---|---|
| diff dir1 dir2 | دو پوشه را به‌صورت سطحی (بدون ورود به زیرپوشه‌ها) مقایسه می‌کند. |
| ‪-r‬, ‪--recursive‬ | به‌طور بازگشتی وارد همه‌ی زیرپوشه‌ها می‌شود و آن‌ها را هم مقایسه می‌کند. |
| ‪-q‬ (همراه با ‪-r‬) | فقط گزارش می‌دهد کدام فایل‌ها متفاوت‌اند، بدون نمایش جزئیات تغییر. |
| ‪-S FILE‬, ‪--starting-file=FILE‬ | مقایسه‌ی پوشه را از فایل مشخص‌شده (به ترتیب الفبایی) شروع می‌کند. |
| ‪-N‬, ‪--new-file‬ | فایل‌های یک‌طرفه را در برابر یک فایل خالی مقایسه می‌کند، به‌جای نمایش پیام «Only in». |
| ‪--unidirectional-new-file‬ | مثل ‪-N‬، اما فقط برای فایل‌های تازه‌ای که در پوشه‌ی دوم اضافه شده‌اند. |
| ‪-x PATTERN‬, ‪--exclude=PATTERN‬ | فایل‌ها یا پوشه‌های منطبق با الگو را از مقایسه کنار می‌گذارد. |
| ‪-X FILE‬, ‪--exclude-from=FILE‬ | الگوهای مستثناشده را از یک فایل متنی می‌خواند. |
| ‪--ignore-file-name-case‬ | بزرگی و کوچکی حروف در نام فایل‌ها را هنگام تطبیق نادیده می‌گیرد. |
| ‪--no-ignore-file-name-case‬ | حساسیت به بزرگی و کوچکی حروف در نام فایل‌ها را دوباره فعال می‌کند. |
| ‪--no-dereference‬ | لینک‌های نمادین را دنبال نمی‌کند؛ خود لینک‌ها مقایسه می‌شوند. |
| ‪--from-file=FILE1‬ | فایل FILE1 را با همه‌ی عملوندهای دیگر مقایسه می‌کند. |
| ‪--to-file=FILE2‬ | همه‌ی عملوندها را با فایل FILE2 مقایسه می‌کند. |

</div>

<div dir="rtl" lang="fa" style="text-align: right;">

## فصل ۵

### <u>diff و patch: ساخت و اعمال وصله</u>

تا این‌جا، از diff فقط برای *دیدن* تفاوت‌ها استفاده کرده‌ایم. اما یکی از مهم‌ترین و پرکاربردترین نقش‌های diff در دنیای واقعی، جایی است که خروجی آن را به یک فایل ذخیره می‌کنیم و از آن به‌عنوان یک «دستورالعمل تبدیل» استفاده می‌کنیم: فایلی که می‌گوید چگونه یک فایل قدیمی را دقیقاً به یک فایل جدید تبدیل کنیم. به این فایل، «وصله» یا patch گفته می‌شود. در این فصل، یاد می‌گیرید چگونه با diff یک وصله بسازید، و چگونه با برنامه‌ی همراه آن، یعنی patch، آن وصله را روی فایل‌های دیگر اعمال کنید.

### ۵.۱ وصله (Patch) چیست و چرا به آن نیاز داریم

فرض کنید روی یک پروژه‌ی نرم‌افزاری کار می‌کنید و یک اشکال (bug) کوچک را در یکی از فایل‌ها پیدا و اصلاح کرده‌اید. حالا می‌خواهید این اصلاح را برای یک همکار بفرستید تا او هم همان تغییر را در نسخه‌ی خودش اعمال کند. دو راه دارید: یا کل فایل اصلاح‌شده را برایش بفرستید و او آن را جایگزین فایل قدیمی‌اش کند، یا فقط *توضیح تغییر* را برایش بفرستید و او خودش این تغییر را روی فایلش اعمال کند.

راه دوم مزیت‌های زیادی دارد: حجم فایل ارسالی بسیار کوچک‌تر است (چون فقط تغییرات فرستاده می‌شوند، نه کل فایل)، و مهم‌تر از آن، اگر همکار شما هم‌زمان تغییرات دیگری روی همان فایل داده باشد، اعمال کردن یک «تغییر مشخص» خطر کمتری نسبت به جایگزین کردن کل فایل دارد. این دقیقاً همان کاری است که وصله (patch) انجام می‌دهد.

یک فایل patch، در واقع چیزی نیست جز خروجی diff، معمولاً در فرمت یکپارچه (که در فصل ۲ دیدیم)، که در یک فایل ذخیره شده است. برنامه‌ای به نام patch (که همراه diffutils عرضه می‌شود) می‌تواند این فایل را بخواند و تغییرات توصیف‌شده در آن را روی فایل مقصد اعمال کند.

### ۵.۲ ساختن یک فایل وصله

ساختن یک وصله، در ساده‌ترین حالت، چیزی بیش از هدایت خروجی diff به یک فایل نیست:

</div>

<div style="text-align:left;">

```
$ diff -u old_version.txt new_version.txt > changes.patch
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اما وقتی می‌خواهیم وصله‌ای برای یک *پروژه‌ی کامل*، شامل چند فایل و چند پوشه، بسازیم، باید از diff بازگشتی که در فصل ۴ دیدیم استفاده کنیم. ترکیب رایج و استاندارد برای این کار، چیزی است که در جامعه‌ی توسعه‌دهندگان به آن «diff -Naur» معروف است:

</div>

<div style="text-align:left;">

```
$ diff -Naur project-old/ project-new/ > my-changes.patch
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

بیایید ببینیم هرکدام از این حروف چه معنایی دارند:

- ‪N‬ (‪--new-file‬): فایل‌هایی که فقط در یکی از دو پوشه هستند را نسبت به یک فایل خالی مقایسه می‌کند، تا محتوای کامل فایل‌های تازه‌ (یا حذف‌شده) هم در وصله بیاید، نه فقط پیام «Only in».
- ‪a‬ (‪--text‬): با همه‌ی فایل‌ها، حتی آن‌هایی که ممکن است اشتباهاً باینری تشخیص داده شوند، مثل فایل متنی رفتار می‌کند.
- ‪u‬ (‪--unified‬): خروجی را در فرمت یکپارچه تولید می‌کند، که همان‌طور که در فصل ۲ گفتیم، امروزه استاندارد اصلی برای وصله‌هاست.
- ‪r‬ (‪--recursive‬): وارد همه‌ی زیرپوشه‌ها می‌شود تا کل ساختار پروژه پوشش داده شود.

این ترکیب چهارگانه، دقیقاً همان چیزی است که در مستندات هسته‌ی لینوکس (Linux Kernel) و بسیاری از پروژه‌های متن‌باز قدیمی، به‌عنوان روش استاندارد ساختن وصله توصیه شده است.

یک نکته‌ی مهم درباره‌ی نام‌گذاری پوشه‌ها: بهتر است دو پوشه‌ای که مقایسه می‌کنید، نام‌هایی با طول یکسان یا حداقل قابل‌تشخیص داشته باشند، مثلاً project-old و project-new، یا حتی ساده‌تر، a و b (که رسم رایج در پروژه‌های Git است). این کار باعث می‌شود مسیرهای داخل فایل وصله خواناتر و یکدست‌تر باشند.

### ۵.۳ ساختار یک فایل وصله

بیایید محتوای یک فایل وصله‌ی ساده را با هم بخوانیم تا بدانیم چه اطلاعاتی در آن نهفته است. فرض کنید این وصله را برای یک تغییر کوچک در یک فایل ساخته‌ایم:

</div>

<div style="text-align:left;">

```
--- a/config.txt	2026-01-15 10:00:00.000000000 +0330
+++ b/config.txt	2026-01-15 10:05:00.000000000 +0330
@@ -1,4 +1,4 @@
 host = localhost
-port = 8080
+port = 9090
 timeout = 30
 debug = false
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

همان‌طور که در فصل ۲ به‌طور کامل توضیح دادیم، خط‌های ‪---‬ و ‪+++‬ نام فایل مبدأ و مقصد را نشان می‌دهند، خط ‪@@ ... @@‬ محدوده‌ی خطوط تغییریافته را مشخص می‌کند، و خط‌های با پیشوند ‪-‬ یا ‪+‬ به‌ترتیب خطوط حذف‌شده و اضافه‌شده هستند. یک فایل وصله می‌تواند شامل چندین چنین بخشی، برای چندین فایل مختلف، پشت‌سرهم باشد؛ برنامه‌ی patch به‌طور خودکار هر بخش را به فایل درست خودش اعمال می‌کند.

### ۵.۴ اعمال کردن یک وصله با دستور patch

حالا که یک فایل وصله داریم، وقت آن رسیده ببینیم چگونه آن را روی نسخه‌ی دیگری از همان فایل یا پروژه اعمال کنیم. برای این کار از برنامه‌ی patch استفاده می‌کنیم که تقریباً همیشه همراه diffutils روی سیستم نصب است.

ساده‌ترین حالت استفاده، دادن نام فایل وصله از طریق ورودی استاندارد است:

</div>

<div style="text-align:left;">

```
$ patch < my-changes.patch
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

برنامه‌ی patch، فایل‌هایی که باید تغییر کنند را از خود متن وصله (از همان خط‌های ‪---‬ و ‪+++‬) استخراج می‌کند و تغییرات را مستقیماً روی آن‌ها اعمال می‌کند. اگر همه‌چیز درست پیش برود، فایل‌های مقصد به‌طور خودکار به‌روزرسانی می‌شوند.

### کنترل عمق مسیر با گزینه‌ی p-

یکی از رایج‌ترین منابع سردرگمی برای تازه‌کارها، گزینه‌ی ‪-p‬ (به همراه یک عدد) در دستور patch است. این گزینه مشخص می‌کند چند سطح از ابتدای مسیر فایل، که در خود وصله نوشته شده، باید نادیده گرفته شود.

به یاد بیاورید که در وصله‌ی نمونه‌ی بالا، مسیر فایل به این شکل نوشته شده بود: ‪a/config.txt‬ و ‪b/config.txt‬. این پیشوندهای ‪a/‬ و ‪b/‬، که diff هنگام مقایسه‌ی دو پوشه با نام‌های a و b اضافه می‌کند (یا Git به‌طور پیش‌فرض همین قرارداد را دنبال می‌کند)، برای برنامه‌ی patch در سیستم شما معنایی ندارند، چون در پوشه‌ی فعلی شما احتمالاً پوشه‌ای به نام a یا b وجود ندارد.

- اگر از ‪patch -p0‬ استفاده کنید، patch سعی می‌کند مسیر را *دقیقاً همان‌طور که در وصله نوشته شده* (یعنی با a/config.txt) پیدا کند، که معمولاً شکست می‌خورد.
- اگر از ‪patch -p1‬ استفاده کنید، به patch می‌گویید یک سطح از ابتدای مسیر (یعنی همان a/ یا b/) را حذف کند و فقط دنبال config.txt در پوشه‌ی فعلی بگردد.

</div>

<div style="text-align:left;">

```
$ patch -p1 < my-changes.patch
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این، دقیقاً همان دستوری است که هنگام کار با وصله‌های تولیدشده توسط Git یا هسته‌ی لینوکس، به‌طور رایج استفاده می‌شود، چون هر دو از قرارداد a/ و b/ پیروی می‌کنند. اگر وصله‌ای دارید که مسیرهای آن ساختار متفاوتی دارند (مثلاً بدون پیشوند a/ و b/)، احتمالاً به ‪-p0‬ نیاز خواهید داشت. بهترین روش این است که ابتدا محتوای وصله را با یک ویرایشگر متن یا با دستور head نگاه کنید تا ساختار مسیرهای آن را ببینید، و بر اساس آن مقدار درست p- را انتخاب کنید.

### آزمایشی اعمال کردن وصله (Dry Run)

پیش از این‌که واقعاً یک وصله را اعمال کنید، خصوصاً اگر مطمئن نیستید دقیقاً چه فایل‌هایی را تغییر می‌دهد، بهتر است ابتدا آن را به‌صورت آزمایشی امتحان کنید. گزینه‌ی ‪--dry-run‬ دقیقاً همین کار را می‌کند: patch وانمود می‌کند وصله را اعمال کرده، اما هیچ فایلی را واقعاً تغییر نمی‌دهد؛ فقط به شما می‌گوید آیا اعمال کردن وصله موفق می‌شد یا نه.

</div>

<div style="text-align:left;">

```
$ patch -p1 --dry-run < my-changes.patch
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر این دستور بدون خطا اجرا شود، می‌توانید با خیال راحت همان دستور را بدون ‪--dry-run‬ دوباره اجرا کنید تا تغییرات واقعاً اعمال شوند.

### ساختن نسخه‌ی پشتیبان هنگام اعمال وصله

اگر می‌خواهید احتیاط بیشتری به خرج دهید، می‌توانید از گزینه‌ی ‪-b‬ یا ‪--backup‬ استفاده کنید تا پیش از تغییر دادن هر فایل، یک نسخه‌ی پشتیبان از آن (معمولاً با پسوند ‪.orig‬) ساخته شود:

</div>

<div style="text-align:left;">

```
$ patch -p1 -b < my-changes.patch
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این کار، برگرداندن فایل‌ها به حالت اولیه را، در صورت بروز مشکل، بسیار ساده‌تر می‌کند.

### بازگرداندن یک وصله (Reverse)

گاهی لازم می‌شود اثر یک وصله را که قبلاً اعمال کرده‌اید، خنثی کنید؛ یعنی فایل را به حالت *قبل* از اعمال وصله برگردانید. برای این کار از گزینه‌ی ‪-R‬ یا ‪--reverse‬ استفاده می‌کنیم:

</div>

<div style="text-align:left;">

```
$ patch -p1 -R < my-changes.patch
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این گزینه دقیقاً همان وصله را می‌خواند، اما جای خطوط ‪-‬ و ‪+‬ را در ذهن خودش برعکس می‌کند، طوری‌که انگار می‌خواهد فایل جدید را به فایل قدیمی تبدیل کند.

### ۵.۵ نکاتی برای ساختن وصله‌های تمیزتر

وقتی وصله‌ای می‌سازید که قرار است برای دیگران ارسال شود یا در یک پروژه‌ی متن‌باز پذیرفته شود، چند نکته کمک می‌کند وصله‌ی شما تمیزتر و راحت‌تر قابل‌بررسی باشد.

نخست، همیشه از فرمت یکپارچه (‪-u‬) استفاده کنید، مگر این‌که دلیل خاصی برای استفاده از فرمت دیگری داشته باشید. این فرمت هم برای انسان و هم برای ابزارها خواناتر است.

دوم، اگر وصله شامل حذف فایل‌های بزرگ است که در نسخه‌ی جدید دیگر وجود ندارند، به‌جای ‪-N‬، از ‪--unidirectional-new-file‬ استفاده کنید تا محتوای کامل فایل‌های حذف‌شده در وصله نیاید (که باعث حجیم شدن غیرضروری وصله می‌شود)؛ در عوض، در توضیحات وصله ذکر کنید کدام فایل‌ها باید پیش از اعمال وصله، به‌صورت دستی حذف شوند.

سوم، از گزینه‌ی ‪--label‬ که در فصل ۲ دیدیم استفاده کنید تا به‌جای تاریخ و ساعت دقیق سیستم خودتان (که برای گیرنده‌ی وصله بی‌معنی است)، برچسب‌های معنادار مثل «نسخه‌ی قدیم» و «نسخه‌ی جدید» در سرآیند وصله بگذارید.

و در نهایت، پیش از ارسال وصله، حتماً آن را روی یک نسخه‌ی تازه از فایل‌های اصلی (که هیچ تغییر دیگری نخورده باشند) تست کنید، تا مطمئن شوید بدون خطا اعمال می‌شود.

### ۵.۶ diff، patch و ابزارهای مدرن

شاید این پرسش برایتان پیش بیاید که با وجود سیستم‌های کنترل نسخه‌ی مدرن مثل Git، آیا اصلاً هنوز لازم است این روش دستی ساختن و اعمال وصله را یاد بگیریم؟ پاسخ این است: بله، به چند دلیل مهم.

نخست، خیلی از ابزارهای مدرن، از جمله خود Git، در پس‌زمینه دقیقاً از همین مفهوم استفاده می‌کنند. دستور git diff، همان خروجی یکپارچه‌ی diff را (با کمی اطلاعات اضافه‌ی مخصوص Git) تولید می‌کند، و دستور git apply در واقع نسخه‌ی داخلی و بهبودیافته‌ی همان patch است که مستقیماً می‌تواند خروجی git diff را اعمال کند:

</div>

<div style="text-align:left;">

```
$ git diff > my-changes.patch
$ git apply my-changes.patch
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

دوم، در بسیاری از موقعیت‌های عملی، مثلاً وقتی به یک سرور دسترسی محدود دارید یا نمی‌خواهید کل تاریخچه‌ی Git را جابه‌جا کنید، ارسال یک فایل وصله‌ی کوچک همچنان ساده‌ترین راه است. برای مثال، توسعه‌دهندگان هسته‌ی لینوکس، حتی امروز، عمدتاً از طریق ایمیل و فایل‌های وصله با هم همکاری می‌کنند، نه از طریق Pull Request در یک پلتفرم گرافیکی.

سوم، درک عمیق این‌که یک وصله چگونه ساخته و خوانده می‌شود، به شما کمک می‌کند وقتی با پیام‌های خطای مبهم Git یا patch روبه‌رو شدید (مثل خطاهای «hunk failed» که وقتی وصله با نسخه‌ی فعلی فایل همخوانی ندارد رخ می‌دهد)، بهتر بفهمید مشکل از کجاست و چگونه آن را رفع کنید.

### ۵.۷ حالا چه؟

در این فصل یاد گرفتید چگونه از diff برای ساختن یک فایل وصله استفاده کنید، چگونه آن وصله را با دستور patch روی فایل‌های دیگر اعمال کنید، و چه نکاتی به ساختن وصله‌های تمیزتر و قابل‌اعتمادتر کمک می‌کنند. همچنین دیدید این مفهوم چطور پایه‌ی ابزارهایی مثل git diff و git apply قرار گرفته است.

در فصل پایانی، نگاهی جامع‌تر به جایگاه diff در دنیای واقعی امروز می‌اندازیم: چگونه Git از این مفاهیم استفاده می‌کند، چگونه می‌توان diff را در اسکریپت‌های شل برای خودکارسازی کارها به کار برد، و با چه ابزارهای مرتبط دیگری ممکن است سروکار داشته باشید.

### برای مرجع بعدی

### ساختن وصله

| دستور | توضیح |
|---|---|
| diff -u old.txt new.txt > file.patch | یک وصله‌ی ساده در فرمت یکپارچه برای دو فایل می‌سازد. |
| diff -Naur old_dir/ new_dir/ > file.patch | یک وصله‌ی کامل و استاندارد برای دو پوشه (با همه‌ی زیرپوشه‌ها) می‌سازد. |
| git diff > file.patch | تغییرات فعلی مخزن Git را در قالب یک فایل وصله ذخیره می‌کند. |

### اعمال کردن وصله

| دستور | توضیح |
|---|---|
| patch < file.patch | وصله را با حدس زدن نام فایل از متن وصله اعمال می‌کند. |
| patch -p1 < file.patch | یک سطح از ابتدای مسیر فایل‌های داخل وصله (مثل a/ یا b/) را نادیده می‌گیرد. |
| patch -p0 < file.patch | مسیر فایل را دقیقاً همان‌طور که در وصله نوشته شده اعمال می‌کند. |
| patch -p1 --dry-run < file.patch | وصله را به‌صورت آزمایشی بررسی می‌کند، بدون تغییر واقعی فایل‌ها. |
| patch -p1 -b < file.patch | پیش از اعمال تغییرات، از هر فایل یک نسخه‌ی پشتیبان (.orig) می‌سازد. |
| patch -p1 -R < file.patch | اثر یک وصله‌ی از‌پیش‌اعمال‌شده را خنثی و فایل را به حالت قبل برمی‌گرداند. |
| git apply file.patch | وصله را با ابزار داخلی Git، سازگار با مخزن فعلی، اعمال می‌کند. |

</div>

## فصل ۶

### <u>diff در دنیای واقعی</u>

در فصل‌های قبل، با خود دستور diff، فرمت‌های خروجی آن، گزینه‌های کنترلی، مقایسه‌ی پوشه‌ها، و ساختن و اعمال وصله آشنا شدید. در این فصل پایانی، نگاهی گسترده‌تر می‌اندازیم به این‌که مفاهیم diff چگونه در ابزارهای مدرن، به‌ویژه Git، به کار رفته‌اند، و چگونه می‌توانید خود diff را در اسکریپت‌های شل و کارهای روزمره‌ی خودکار به کار بگیرید.

### ۶.۱ diff در دل Git

اگر امروز از یک سیستم کنترل نسخه استفاده می‌کنید، به احتمال زیاد Git است. و شاید جالب باشد بدانید که وقتی دستور git diff را اجرا می‌کنید، Git در واقع پیاده‌سازی داخلی خودش از یک الگوریتم diff را اجرا می‌کند، نه این‌که مستقیماً از برنامه‌ی diff سیستم شما استفاده کند. اما مفهوم و خروجی آن، دقیقاً همان فرمت یکپارچه‌ای است که در فصل ۲ به‌طور کامل بررسی کردیم.

</div>

<div style="text-align:left;">

```
$ git diff
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دستور، تفاوت بین فایل‌های تغییریافته در دایرکتوری کاری شما و آخرین نسخه‌ی ثبت‌شده (commit) را در همان فرمت یکپارچه نشان می‌دهد که با خط‌های ‪---‬، ‪+++‬، سرآیند ‪@@ ... @@‬، و علامت‌های ‪-‬ و ‪+‬ کاملاً برایتان آشناست.

می‌توانید مشخص کنید Git کدام دو نسخه را با هم مقایسه کند؛ برای مثال، تفاوت بین دو commit:

</div>

<div style="text-align:left;">

```
$ git diff commit1 commit2
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

یا تفاوت بین دو شاخه (branch):

</div>

<div style="text-align:left;">

```
$ git diff main feature-branch
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

یا تفاوت مربوط به یک فایل مشخص:

</div>

<div style="text-align:left;">

```
$ git diff -- path/to/file.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### الگوریتم‌های مختلف diff در Git

نکته‌ی جالب این است که Git، برخلاف دستور استاندارد diff که تنها یک الگوریتم داخلی دارد، از چهار الگوریتم مختلف برای پیدا کردن تفاوت‌ها پشتیبانی می‌کند:

- myers: الگوریتم پیش‌فرض Git، بر اساس همان روش حریصانه (greedy) که در فصل ۱ درباره‌ی الگوریتم LCS صحبت کردیم. این الگوریتم تضمین می‌کند کمترین تعداد ممکن خط تغییریافته را پیدا کند، اما همیشه خروجی «قابل‌فهم‌ترین» را از دید انسان تولید نمی‌کند.
- minimal: نسخه‌ی بهبودیافته‌ی myers که وقت بیشتری صرف می‌کند تا مطمئن شود کوچک‌ترین دیف ممکن پیدا شده است؛ شبیه گزینه‌ی ‪-d‬ یا ‪--minimal‬ که در فصل ۳ درباره‌ی دستور diff دیدیم.
- patience: الگوریتمی که توسط برام کوهن (Bram Cohen)، خالق پروتکل BitTorrent، ابداع شد. این الگوریتم، به‌جای تمرکز صرف بر کمترین تعداد خط تغییریافته، سعی می‌کند خطوطی که در هر دو فایل *فقط یک‌بار* ظاهر شده‌اند را به‌عنوان «لنگر» (anchor) در نظر بگیرد، که معمولاً برای خواندن تغییرات کد برنامه‌نویسی، خروجی به‌مراتب خواناتری تولید می‌کند.
- histogram: نسخه‌ی پیشرفته‌تر و معمولاً سریع‌تر patience، که امروزه در بسیاری از پروژه‌ها به‌عنوان جایگزین پیش‌فرض ترجیح داده می‌شود.

می‌توانید الگوریتم مورد استفاده را برای یک دستور خاص تغییر دهید:

</div>

<div style="text-align:left;">

```
$ git diff --diff-algorithm=histogram
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

یا آن را به‌طور دائمی برای همه‌ی مخازن (repository) خود تنظیم کنید:

</div>

<div style="text-align:left;">

```
$ git config --global diff.algorithm histogram
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

نکته‌ی مهم این است که انتخاب الگوریتم، هیچ تأثیری روی *محتوای* واقعی که Git ذخیره یا ثبت می‌کند ندارد؛ فقط روی نحوه‌ی *نمایش* تفاوت‌ها و نحوه‌ی تولید وصله (patch) اثر می‌گذارد. برای کدهای برنامه‌نویسی که توابع و بلوک‌های جابه‌جاشده در آن‌ها زیاد است، بسیاری از برنامه‌نویسان ترجیح می‌دهند از histogram یا patience استفاده کنند، چون خروجی خواناتری، به‌خصوص هنگام مرور کد (code review)، تولید می‌کند.

### از git diff به فایل وصله

همان‌طور که در فصل ۵ دیدیم، خروجی git diff را می‌توان مستقیماً به یک فایل وصله تبدیل کرد و با git apply روی نسخه‌ی دیگری اعمال کرد. علاوه بر این، Git ابزار قدرتمندتری هم به نام git format-patch دارد که، به‌جای فقط تفاوت متنی، یک یا چند وصله‌ی کامل شامل اطلاعات کامیت (نویسنده، پیام، تاریخ) می‌سازد؛ این وصله‌ها را می‌توان با git am روی مخزن دیگری اعمال کرد و مستقیماً commit جدیدی از آن‌ها ساخت. این دقیقاً همان روشی است که پروژه‌هایی مثل هسته‌ی لینوکس، حتی امروز، برای همکاری از طریق ایمیل استفاده می‌کنند.

### ۶.۲ استفاده از diff در اسکریپت‌های شل

یکی از قدرت‌های اصلی diff این است که خروجی و کد بازگشتی آن، طوری طراحی شده‌اند که به‌راحتی در اسکریپت‌های شل قابل استفاده باشند. بیایید چند الگوی رایج را ببینیم.

### بررسی این‌که آیا فایلی تغییر کرده یا نه

با استفاده از کد بازگشتی که در فصل ۱ دیدیم، می‌توانید به‌سادگی در یک اسکریپت شرط بگذارید:

</div>

<div style="text-align:left;">

```
if diff -q "$file1" "$file2" > /dev/null; then
    echo "Files are identical"
else
    echo "Files differ"
fi
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### پشتیبان‌گیری هوشمند: فقط وقتی چیزی تغییر کرده کپی کن

یک کاربرد رایج دیگر، ساختن یک اسکریپت پشتیبان‌گیری است که فقط وقتی فایل مقصد واقعاً تغییر کرده، آن را بازنویسی می‌کند (که برای جلوگیری از تغییر بی‌دلیل timestamp فایل‌ها مفید است):

</div>

<div style="text-align:left;">

```
#!/bin/bash
SRC="config.txt"
DST="/etc/backup/config.txt"

if [ ! -f "$DST" ] || ! diff -q "$SRC" "$DST" > /dev/null 2>&1; then
    cp "$SRC" "$DST"
    echo "File copied, because it had changed."
else
    echo "No copy needed, content is identical."
fi
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### مقایسه‌ی خروجی دو اجرای مختلف یک برنامه

diff همچنین برای مقایسه‌ی خروجی دو نسخه از یک برنامه، مثلاً در تست‌های رگرسیون (regression testing)، بسیار مفید است. می‌توانید خروجی یک برنامه را در یک فایل ذخیره کنید، تغییری در کد بدهید، دوباره خروجی را بگیرید، و این دو را با هم مقایسه کنید تا مطمئن شوید تغییر شما رفتار برنامه را به‌طور ناخواسته عوض نکرده است:

</div>

<div style="text-align:left;">

```
$ ./my_program < input.txt > output_before.txt
# ... a change is made to the code ...
$ ./my_program < input.txt > output_after.txt
$ diff -u output_before.txt output_after.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر این دستور هیچ خروجی‌ای نداشته باشد (یعنی کد بازگشتی آن ۰ باشد)، مطمئن می‌شوید تغییر شما رفتار قابل‌مشاهده‌ی برنامه را عوض نکرده است.

### مقایسه‌ی خروجی دستورها با فرآیند جایگزینی (Process Substitution)

در شل Bash، می‌توانید حتی بدون نیاز به ساختن فایل‌های موقت، خروجی دو دستور مختلف را مستقیماً با diff مقایسه کنید، با استفاده از یک ویژگی به نام «جایگزینی فرآیند» (process substitution):

</div>

<div style="text-align:left;">

```
$ diff <(ls dir1) <(ls dir2)
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دستور، خروجی دو دستور ls را، بدون این‌که نیاز باشد آن‌ها را دستی در فایل ذخیره کنید، مستقیماً با هم مقایسه می‌کند. این ترفند به‌خصوص برای مقایسه‌ی سریع خروجی دو دستور، مثل فهرست کردن پکیج‌های نصب‌شده روی دو سرور مختلف، بسیار کاربردی است:

</div>

<div style="text-align:left;">

```
$ diff <(ssh server1 dpkg -l) <(ssh server2 dpkg -l)
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۶.۳ ابزارهای مرتبط و مکمل diff

diff بخشی از یک خانواده‌ی بزرگ‌تر از ابزارهاست که هرکدام برای هدف مشخصی طراحی شده‌اند. آشنایی با این ابزارها به شما کمک می‌کند بدانید چه زمانی diff مناسب‌ترین انتخاب است و چه زمانی باید سراغ ابزار دیگری بروید.

- cmp: برخلاف diff که خط‌به‌خط مقایسه می‌کند، cmp دو فایل را بایت‌به‌بایت مقایسه می‌کند و اولین نقطه‌ی اختلاف را گزارش می‌دهد. برای فایل‌های باینری که نمی‌خواهید محتوایشان به‌صورت متنی تفسیر شود، cmp گزینه‌ی دقیق‌تری است.

</div>

<div style="text-align:left;">

```
$ cmp file1.bin file2.bin
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

- diff3: نسخه‌ای از diff که سه فایل را هم‌زمان با هم مقایسه می‌کند؛ این ابزار پایه‌ی بسیاری از عملیات‌های merge در سیستم‌های کنترل نسخه است، جایی که باید یک فایل پایه (base) و دو نسخه‌ی تغییریافته از آن را با هم آشتی دهید.

- sdiff: دو فایل را در فرمت کنار هم (شبیه به diff -y) نمایش می‌دهد، اما با قابلیت تعاملی برای آشتی دادن (merge) تفاوت‌ها به‌صورت دستی.

- wdiff: به‌جای مقایسه‌ی خط‌به‌خط، تفاوت‌ها را در سطح *کلمه* نشان می‌دهد؛ این برای مقایسه‌ی متن‌های نوشتاری (مثل مقالات یا کتاب‌ها)، جایی که تغییرات معمولاً در حد چند کلمه‌ی وسط یک پاراگراف هستند نه کل خط، بسیار مناسب‌تر از diff معمولی است.

- colordiff: یک پوشش (wrapper) دور diff که خروجی آن را به‌طور خودکار رنگی می‌کند؛ اگر نسخه‌ی diff شما گزینه‌ی ‪--color‬ داخلی را پشتیبانی نمی‌کند (نسخه‌های بسیار قدیمی)، colordiff جایگزین مناسبی است.

می‌توانید درباره‌ی هرکدام از این ابزارها با دستور man اطلاعات بیشتری کسب کنید، برای مثال:

</div>

<div style="text-align:left;">

```
$ man cmp
$ man diff3
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۶.۴ حالا چه؟

در طول این کتاب، سفری کامل از ابتدایی‌ترین استفاده‌ی diff تا کاربردهای پیشرفته‌ی آن داشتیم. با تاریخچه و منطق پشت diff آشنا شدید، فرمت‌های مختلف خروجی آن را یاد گرفتید، دیدید چگونه رفتار آن را با ده‌ها گزینه کنترل کنید، چگونه پوشه‌های کامل را با هم مقایسه کنید، چگونه از آن برای ساختن و اعمال وصله استفاده کنید، و در نهایت، جایگاه آن را در ابزارهای مدرنی مثل Git دیدید.

دستور diff، با وجود سادگی ظاهری‌اش، یکی از آن ابزارهایی است که هرچه بیشتر با آن کار کنید، بیشتر متوجه می‌شوید چقدر در جاهای مختلف زندگی روزمره‌ی یک برنامه‌نویس یا مدیر سیستم حضور دارد؛ از یک مقایسه‌ی ساده‌ی دو فایل پیکربندی گرفته تا موتور پشت صحنه‌ی هر Pull Request که در Git می‌بینید.

اگر می‌خواهید عمیق‌تر شوید، صفحه‌ی راهنمای کامل GNU diffutils (نه فقط man page کوتاه، بلکه مستندات کامل Texinfo آن) منبع بسیار خوبی برای ادامه‌ی مسیر است:

و اگر با Git کار می‌کنید، مطالعه‌ی مستندات git-diff و آزمایش کردن الگوریتم‌های مختلف روی پروژه‌های واقعی خودتان، بهترین راه برای درک عمیق‌تر این مفاهیم در عمل است.

### برای مرجع بعدی

### diff در Git

| دستور | توضیح |
|---|---|
| git diff | تفاوت فایل‌های تغییریافته‌ی دایرکتوری کاری را نسبت به آخرین commit نشان می‌دهد. |
| git diff commit1 commit2 | تفاوت بین دو commit مشخص را نشان می‌دهد. |
| git diff branch1 branch2 | تفاوت بین دو شاخه را نشان می‌دهد. |
| git diff --diff-algorithm=NAME | الگوریتم diff را برای این دستور تغییر می‌دهد (myers، minimal، patience، histogram). |
| git config --global diff.algorithm NAME | الگوریتم diff پیش‌فرض را برای همه‌ی مخازن تنظیم می‌کند. |
| git format-patch | برای هر commit، یک فایل وصله‌ی کامل (همراه اطلاعات کامیت) می‌سازد. |
| git am | وصله‌های ساخته‌شده با format-patch را اعمال کرده و commit می‌سازد. |

### الگوهای رایج اسکریپت‌نویسی

| الگو | توضیح |
|---|---|
| diff -q a b > /dev/null | بررسی یکسان بودن دو فایل، بدون نمایش خروجی، برای استفاده در شرط. |
| diff <(cmd1) <(cmd2) | مقایسه‌ی مستقیم خروجی دو دستور، بدون ساختن فایل موقت (ویژه‌ی Bash). |

### ابزارهای مرتبط

| ابزار | توضیح |
|---|---|
| cmp | مقایسه‌ی بایت‌به‌بایت دو فایل؛ مناسب فایل‌های باینری. |
| diff3 | مقایسه و آشتی دادن سه فایل هم‌زمان؛ پایه‌ی عملیات merge. |
| sdiff | نمایش کنار هم دو فایل با قابلیت آشتی دادن تعاملی. |
| wdiff | مقایسه‌ی تفاوت‌ها در سطح کلمه، مناسب متن‌های نوشتاری. |
| colordiff | پوششی برای رنگی کردن خروجی diff در نسخه‌های قدیمی. |
